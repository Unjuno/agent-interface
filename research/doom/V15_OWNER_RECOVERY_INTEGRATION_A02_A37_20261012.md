# V15 owner crash recovery findings, A02–A32

The V15 process-owner experiments A02–A15 are indexed in their per-allocation folders and PR #8876. They established a real owner-service-death stuck-input case (A14), a guarded but manually driven emergency release primitive (A15), and multiple setup stops. This continuation adds a durable owner-state ledger and supervisor recovery path.

The bounded repair adds a fsynced per-operation intent/ack ledger, process start-tick identity, strict reconstruction of possibly held inputs, focus/surface/geometry and pointer checks, process-death verification, restricted XTEST releases, independent state/event observation, and durable verified or unverified receipts. The outer V39 success and failure-cleanup paths call `verify_or_recover_owner_process`; they first prefer the existing owner close receipt and use emergency recovery only after the owner receipt gate times out.

Local verification: the focused process-owner / cleanup suite passes 30 tests. A24/A25 exercise two keys and Button1 in isolated WSL2/Xvfb; A26 exercises the actual outer failure-cleanup object with owner-process death and emergency release; A32 exercises normal child finish, reader retirement, and generation-bound receipt acceptance. A32's synthetic sidecars do not establish real V39 scorer/owner-events behavior. The evidence does not prove physical-device input attribution, mixed physical/XTEST ownership, multi-button or mixed-focus recovery, the full V39 CLI/scorer/game path, model feedback, or task-effect correctness. Keep the live MAP01 allocation unassigned and this research classified as method-scoped, not product-level computer-control completion.

## A35: core-X11 shared-key source attribution (2026-10-12)

`PASS_METHOD_SCOPED`. With the global key initially up, a separate XTest client pressed `a`; the focus-window owning X connection observed KeyPress and query_keymap showed down. The real process owner then admitted the same key and performed its verified explicit KeyRelease. The focus-owning connection observed KeyRelease and query_keymap showed up while the external client's test-side logical-hold flag remained true. The owner exited 0 and wrote a verified empty recovery receipt. Candidate, plan, and owner dependencies were frozen before execution; the independent pre-run gate and in-run gate both verified hashes, and the runner hash was bound through HARNESS.json. Exactly one invocation, no retries. Raw evidence and hashes are in `research/doom/v39_v15_xvfb_shared_key_source_a35_20261012/`.

Interpretation is limited to private TCP-disabled Xvfb using core XTest: the server keymap and transition events are global and do not preserve independent per-client held state. It does not establish physical keyboard or mixed physical/XTEST behavior, XI2/raw-input behavior, application behavior, game control, or task-effect correctness. A33 remains a setup STOP; A34 remains a provenance/observation STOP. The result strengthens the need for exclusive display ownership or source-aware arbitration before releasing keys on shared input paths, but does not validate any physical-device mitigation.
