# #59 producer-epoch freshness boundary

A bounded source-level counterexample using the exact current-main `ProgressClockV2` implementation. Under two upstream histories that differ only in provenance—sample from the current episode versus a stale return from the previous episode—the scorer receives the same two typed samples and emits the same event: both a one-kill transition and a non-exit terminal transition are accepted identically. Both histories have the same numeric update tic (74); the producer episode identity differs. The typed API exposes only local `sample_ns` and scorer values, with no source episode/update epoch.

This demonstrates a precise limitation: under the stated stale-return possibility, the clock cannot establish freshness or current-episode attribution from monotonic receipt time and state values alone. An identity-bearing source epoch (and update ID/tic within it) must be validated upstream before scorer effects can be attributed to the current run. It does not show that ViZDoom actually returns stale data; it is a distinguishability counterexample, not an empirical failure.
