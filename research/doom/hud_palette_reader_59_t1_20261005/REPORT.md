# Palette-aware HUD repair with explicit leading-background checks

This ordinary repair follows the actual retained palette mismatch in [#7975](https://github.com/Unjuno/agent-interface/pull/7975). A new opt-in `doom_hud_signal_v4.py` reads complete numbers under each of the fourteen hash-bound WAD palettes, retains the existing glyph score 0.80/margin 0.05 and geometry, and refuses incompatible complete values. The current V39 controller still imports V3; this package does not switch its runtime or authorize a live allocation.

The simple whole-number palette bank was insufficient: generated mixed-palette `100` became observed 0, and partially occluded 147 became 47. A single foreground-colored pixel in a leading blank also passed. All three first failures and the naive source are retained. A first background repair rejected two cases but still accepted the partial glyph because gray/black glyph edges can also occur elsewhere in STBAR; that source and failed output are retained too.

V4 now checks each omitted leading slot against the same palette's WAD STBAR background. It requires the unchanged 0.80 exact fraction, background-only colors, every pixel color to occur within the canonical background's one-output-pixel neighborhood, and no threshold-passing glyph evidence in that slot under any palette. This last check is a veto; it never assembles digits from different palettes. Any ambiguous glyph or conflicting complete value returns UNKNOWN. File and in-memory paths share the same reader; positional signal arguments and metadata-before-file-access behavior are preserved.
