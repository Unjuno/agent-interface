# V39 health-invalidation to planner-interrupt composition A01

This construction experiment joins two previously separate tests: the current authored health guard and the current cancel-before-interrupt planner path. It drives a synthetic paired HUD observation through the frozen current-main `build_cover_monitor`, then passes a hard invalidation through the actual `cancel_invalidated_cover` helper and `PersistentPlannerAdapter` using deterministic fakes.

The hard-crossing case starts at health 100 with critical floor 80 and authored maximum loss 12; health 84 crosses the derived floor 88. It must write the executor cancel before requesting planner interrupt, require a verified empty terminal, then reject the old answer when a completed response arrives. A paired soft case uses maximum loss 16, where health 84 equals the derived floor; it must preserve the policy and leave the pending answer eligible without cancel or interrupt. A third hard-crossing case forces executor cancel-write failure; the adapter still attempts planner interruption and the controller reports the local cancel error after verifying terminal release.

The separate audit pins four source/document inputs, independently checks all event-order and disposition claims, and includes mutations for event order, stale-answer eligibility, and failure-error ordering. The first event-order mutation test did not actually swap the two events; its failure is preserved in `TEST_INITIAL_FAILURE.txt`. After correcting the swap, a second test run showed the auditor correctly rejected the mutation while the test's expected error text was too strict; that assertion failure is also preserved. The candidate and original `AUDIT.json` remain unchanged. Corrected tests and the stricter additive `AUDIT_V2.json` use a true event swap and require monitor → executor cancel → planner interrupt → empty terminal → helper disposition → answer arrival → classification order. The latest additive `AUDIT_V3.json` additionally enforces helper disposition ordering after terminal and before answer arrival. This tests control-flow composition only; it does not test real HUD extraction time, App Server behavior, physical release, useful feedback, bounded recovery, or task effect.
