## H/T/D/C/U

**H — Hypothesis.** With PR #8691's lease-safe delayed-UP cancellation and terminal custody propagation integrated, the current V39/V15 runtime can cancel the exact active cover when a fresh typed health observation crosses that cover's hard validity floor while a slow planner turn is pending. It will discard the dependent answer, release the cover's inputs through the owner, and accept a bounded recovery plan only from a newer observation. The independent progress scorer will establish whether useful task feedback occurs while inference is pending.

**T — Treatment.** Execute one live episode on the exact threat-contact fixture using `gpt-5.6-luna` at low effort, game seed `990619`, at most 10 planner decisions, and the existing 600-second in-game timeout. The 10-decision limit is increased from A02's six so the same fixed exposure can continue beyond the four completed A02 turns, reach a model-authored hard-health floor if the trajectory permits, and leave at most two decisions for bounded recovery. Use the first-party host Codex app-server through the frozen host/VM JSONL relay. Xvfb is launched by the guest command with `-screen 0 1280x800x24 -nolisten tcp`. No prewarming, manual gameplay, alternate input path, retry, or in-place repair.

**D — Decision and measurements.** Retain model requests/responses and usage, controller events, policy and running-action invalidation receipts, typed health/ammo observations and paired RGB artifacts, per-key release-batch deliveries and owner-thread key-up receipts, independent scorer samples/events, score, terminal, host/guest output, and hashes. A hard-guard exposure requires a `health:below_hard_minimum` invalidation from a fresh typed pair while a model turn is pending. A correct cancellation requires a matched cover ID and intent token, the dependent planner answer to be ineligible/discarded, no stale plan admission, and X11 owner key-up evidence followed by verified empty release and terminal closure. A useful-feedback event is limited to a scorer-only `KILL_COUNT_INCREASE` or `MAP_EXIT` event; report its first timestamp relative to each pending model interval. Bounded recovery requires a plan admitted from a typed observation sequence newer than the invalidation sequence within at most two later planner decisions. Report health, ammo, kills, progress, release evidence, and terminal outcome separately.

**PASS** requires all of the hard-guard, matching cancellation, complete per-key/empty release, no-stale-answer, useful-feedback-during-pending-inference, and bounded fresh-recovery conditions above. **FAIL** is a reproduced cancellation/lease error, missing or mismatched release custody, stale answer admitted after invalidation, or an unverified final release. **HOLD** means the fixed episode ends without hard-guard exposure or without enough fresh decisions for the bounded recovery, or no independent useful event occurs during a pending planner interval. **STOP** preserves the first runtime/model failure, death, MAP01 exit, timeout, or other terminal outcome without retry.

**C — Controls.** Keep the A02 fixture, seed, model, effort, map, skill, V39 controller, schema, host relay, and input restrictions. The only prospective changes are (1) using exact current-main source after PR #8691's reviewed integration, (2) a new allocation ID, (3) the dedicated VM's qualified ViZDoom 1.3.0/Xvfb runtime, and (4) the preregistered 10-decision cap for guard exposure and at most two recovery decisions. Freeze every transitive runtime source hash, runner, auditor, fixture input, WAD, CLI binary/version, VM identity, display command, output path, and stop rule before starting the model or game.

**U — Uncertainty and scope.** One episode is descriptive and cannot establish a rate, survival benefit, causal advantage, or MAP01 completion. Typed HUD evidence is not a general enemy detector. X11 key-up receipts establish server-side event processing and observed server state, not hardware key state or game consumption. The scorer's progress events are task progress, not proof that the returned model action was correct. A02 remains a preserved failure and is never retried; A03 is a distinct prospective allocation with the integrated fix and a wider fixed decision budget.
