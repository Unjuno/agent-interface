## WSL Windows-executable interop follow-up

- **H:** When V39 runs under WSL but launches the Windows Codex executable, an explicit Linux `CODEX_HOME` must reach the Windows process with drive-path translation. Without that bridge, the Windows process can select its default profile instead of the isolated profile that the launcher inspected.
- **T:** First wrote a regression for the WSL child environment and observed it fail because no environment builder existed. Added a bounded `WSLENV` merge for `CODEX_HOME/p` only when `WSL_INTEROP` is present and command[0] is a Windows `.exe` whose command[1] is `app-server`; reject missing or Windows-formatted `CODEX_HOME` before process start. A separate regression keeps the existing WSL Node/npm fallback exempt from this requirement. Then ran the production V39 client from WSL2 Ubuntu/Python 3.12.3 against Codex `0.162.0-alpha.17.2` (SHA256 `d13914ced6c7af174d8d638db938284231227312104b06a25e9608c632a7daec`) and a dedicated, credential-free temporary `CODEX_HOME` containing an explicitly enabled fake MCP.
- **D:** PASS. The App Server reported the isolated Windows profile path, initialized, started an ephemeral thread with a `wslpath -w` directory, returned the three stdio streams closed after client shutdown, and did not create the fake-MCP sentinel. Unit tests reject absent/wrong profile paths and preserve the WSL Node/npm fallback. The test did not start a model turn, GUI, game process, or Doom input. The Windows-focused V39 suite passes 24/24 in normal Python and under `py -O`.
- **C:** An earlier diagnostic used a Windows-formatted `CODEX_HOME` string inside the Linux Python process; that path was not readable by the launcher and did not reach the Windows child as intended. Its initialize response reported the default Windows profile, so the probe was stopped before `thread/start`; no such result is counted as isolated-profile evidence. The corrected test uses a Linux path plus WSL path translation and verifies the reported Windows profile exactly.
- **U:** WSL launcher compatibility is now established for initialize, ephemeral thread start, selected profile propagation, declared-MCP suppression, and pipe closure. Live health/ammo observations, interruption timing, physical key release, useful feedback, recovery, ammunition/progress, terminal result, and Issue #59 successor acceptance remain unverified. WSLc containers were not used; the current Issue #7924 ownership hold and separate live-lane gate remain in force.

The extra regression and raw WSL artifacts are retained at `D:\codex-research\v39-wsl-appserver-smoke-20261012`; the latest raw journal is `wslenv-mcp-autoforward-v4.jsonl` and the executable probe is `wslenv-mcp-autoforward-v4.py`. ## Review correction

The first A02 draft proposed `-c mcp_servers={}` based on the A01 local preflight note. Review identified that this contradicted the repository's retained startup study, which explicitly tested the override and found it did not clear configured servers. The first draft's direct-mode unit test only checked argument presence and could not establish clearing behavior. The follow-up also found that emitting overrides for names absent from a Codex config causes `invalid transport`. The launcher now derives only configured server names, and the actual fake-server and isolated-profile probes verify the runtime effect. This remains launcher validation, not live control.
