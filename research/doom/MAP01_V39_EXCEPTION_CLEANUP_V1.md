# MAP01 v39 pre-input exception cleanup

**H — Hypothesis:** When v39 refuses bounded passive source refresh or rejects a typed health source before admitting the next cover program, the controller can preserve the original failure and still request the child session's normal finish path, retain the post-control score and owner-close receipt, and record whether all accepted programs have verified empty-release terminals and both child and planner shutdown completed.

**T — Minimum discriminator:** Exercise the cleanup helper with inert process/planner boundaries, a delayed stdout reader, a non-retiring reader, and a real child whose stdin pipe is filled to `EAGAIN` while the child does not read it. PASS requires the original exception identity to survive; pipe pressure must not prevent child escalation, planner close, or failure-report publication; incomplete finish/scorer evidence must remain false.

**D — Result:** PASS for eight cleanup-helper tests, two cleanup portability/stage diagnostics, seven wait-loop tests, thirteen source-refresh tests, and Python compilation plus `git diff --check`. The cleanup test module remains discoverable when `fcntl` imports are unavailable; this models Windows test discovery only and does not establish Windows pipe behavior. Failure-stage receipts now advance after the typed health/ammo check through planner input/turn/result validation, action admission/guard/execution, session finish and score, reaping, planner close, stderr capture, and report preparation/write. A stage-order regression verifies the critical boundaries. A real Python child with a full POSIX stdin pipe timed out the bounded finish sender, then was terminated and reaped; planner close ran, the finish sender retired, the original exception survived, and `cleanup_complete` stayed false. The delayed-reader case proves terminal classification happens after reader join; the still-live-reader case fails closed. Existing v39 coast tests could not import because Pillow is unavailable in this host environment. This is local lifecycle-construction evidence only; no VizDoom, app-server model call, GUI, or gameplay action ran.

**C — Competing explanation:** The pipe test uses a POSIX Python child and cannot establish Windows/WSLc pipe behavior, a real scorer/backend failure, or every non-cooperative session. A finish request alone does not prove input termination; the report separately checks matching terminal and empty-release records.

**U — Uncertainty:** The helper is wired around controller setup, source refresh (which submits passive `observe` programs), and cover construction before a new movement/action program is admitted. The failure receipt classifies only stdout events observed after a fully retired, error-free reader; it does not independently verify physical input release. It does not repair exceptions during active movement/action or guarantee planner-child termination beyond the client close contract. WSLc/native Windows pipe pressure is untested; the separate stderr-capture change remains unmerged.

On cleanup, v39 writes `controller-failure.json` after teardown. `cleanup_complete` requires a post-control score event and file, child exit, successful planner close, verified owner records ending in `reason=close`, and an empty verified release terminal for every accepted program observed by the parent after the stdout reader exits cleanly; otherwise it is false. The initiating exception is re-raised unchanged and cleanup failures are attached as notes and retained in the report. Reader join is bounded, so a still-live or failed reader forces event-derived evidence to remain incomplete.
