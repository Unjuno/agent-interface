# Issue #59 startup-stderr custody diagnostic T0

## H / T / D / C / U

**H.** For a child session that exits or times out before emitting `ready`, a concurrently drained, fixed-memory stderr collector can retain a bounded diagnostic (prefix, tail, byte count, full-stream SHA-256) while preserving the primary startup/timeout outcome and avoiding pipe-capacity deadlock. This tests the failure-diagnosis boundary exposed by `controller-visual-01`; it does not diagnose that retained run's actual cause.

**T.** In one frozen OrbStack/Linux container invocation, run four deterministic subprocess cases serially: (1) child writes a short recognizable error then exits 19 before `ready`; (2) child writes exactly 262,144 bytes (> ordinary pipe capacity) then exits 23 before `ready`; (3) child writes a startup diagnostic and stays alive without `ready` until the parent deadline, then is terminated; (4) child emits one valid `ready` event, writes a nonfatal diagnostic and exits 0. Drain stderr asynchronously at process start. Retain only the first and last 4,096 bytes while hashing/counting the full stream. Write candidate output once; run an independently implemented auditor once against raw output. Construction tests use synthetic audit fixtures and do not spawn subprocesses or produce formal output.

**D.** `PASS_METHOD_SCOPED` only if the exact four rows have the declared primary outcomes and process exits/signals; all stderr byte counts, SHA-256, bounded prefix/tail and truncation flags match independently recomputed fixtures; the ready event is exact; each row completes within 2 seconds; and all four frozen mutations are rejected by the auditor. Missing/truncated capture metadata, wrong primary outcome, malformed/incomplete rows, timeout/deadlock, or accepted mutation is `FAIL_METHOD`. No retry after formal invocation.

**C.** A simple synchronous read after child exit may suffice for small stderr. A background drainer with bounded retained bytes may add enough complexity that a simpler spool-to-file design is preferable. The actual `controller-visual-01` could have failed for unrelated import, fixture, engine, or environment reasons.

**U.** Synthetic Node child processes only; no VizDoom, X server, model/provider call, GUI, OS input, threat exposure, useful-effect scoring, gameplay, cleanup integration, or physical-key timing. This qualifies only an isolated stderr-capture protocol, not the current v39 controller or Issue #59's live threat/recovery gate.

## Provenance and boundaries

Issue #59 records `controller-visual-01` as `STOP_SESSION_BEFORE_READY`: its child exited before `ready`, the exception path did not persist child stderr, and the retained evidence did not prove root cause. A later current-main visual-controller run was retained by PR #7570 and completed two model decisions, but ended HOLD with no subsequent recovery decision and zero positive scorer events. Thus this diagnostic does not reopen the startup STOP as the present live blocker and does not diagnose its actual cause. The prior STOP remains immutable; this T0 uses fresh child processes and tests a narrowly separated method property that would make future startup failures diagnosable. Existing #6944 startup-cleanup review and the many open #59 source/telemetry PRs were inspected; this package does not edit their paths or rerun their native/formal allocations.
