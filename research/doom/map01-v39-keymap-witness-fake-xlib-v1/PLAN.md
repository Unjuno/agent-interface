# Plan

## H / T / D / C / U

**H:** The v39 `InputOwner` v10 plus its `InputOwner` v3 transition wrapper can support repeated per-key witness rows with a caller-assigned occurrence ID and 32-byte keymap snapshots around the owner call acknowledgments.

**T:** Import the exact v10 source from current main and the exact v3 wrapper from PR #7376 head `0f112dcae1e3b108ae2eecddebd95b829b8fbffa`. Route two `W` down/up occurrences through the actual owner queue while an in-memory fake Xlib/XTest server supplies keymap bits. Record a fresh occurrence ID and full bitmap before down, after down admission, and after the explicit up receipt. Close the owner and retain its final empty-state record.

**D:** PASS this construction rung only if both occurrences have distinct IDs; each witness sequence is `false → true → false`; all maps are 32 bytes and their recorded bits agree; both down admissions and up receipts are present; both release receipts remain ordinary and owner-history-complete; final cleanup is verified empty.

**C:** This does not exercise Xlib/XTest, synchronization, or a keymap implementation from an actual X server. The fake server changes its bitmap synchronously when the actual owner source calls the fake `xtest.fake_input`; it is a control-flow/API integration fixture.

**U:** Actual Xvfb/X server observations, key event delivery, physical keyboard state, application receipt/useful feedback, task effect, recovery coverage, and latency remain unmeasured. The occurrence ID is generated by the fixture; the v10 admission row itself does not provide a unique key-occurrence ID. No live allocation is authorized by this result.
