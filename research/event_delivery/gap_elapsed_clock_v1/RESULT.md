# 検証結果 — 欠落イベント通知の観測回数と経過時間

## 結論

**PASS_LOCAL_CLOCK_BOUNDARY_SCOPED**。ローカル事前登録した72ケースを一回だけ実行し、72/72ケースを独立監査で再構成した。runner終了コード0、各worker終了コード0、破損対照11/11拒否、固定した20ファイルのSHA-256一致。GitHubへの事前登録・公開・PR・main反映は実行していない。

3回観測の条件は観測頻度によって通知までの時間が変わる。80 msの経過条件は早すぎる通知を防いだが、ポーリングが止まっている間に自動通知するものではない。どちらにも「必ず80 ms以内にホストへ届く」という保証はない。#926は元から時間保証を主張しておらず、その旧PASSを変更・否定する結果ではない。

elapsed方策で初回通知が生じた27の欠落状態の最小経過時間は **80.173 ms**。監査は80 ms以上であることに加え、実際の最初の適格pollで通知していることを確認した。paused条件が示すとおり、経過時間の比較だけでは自律的な起床・配信期限は成立しない。

## 到着・保持・通知の区別

`late40`の実際のE4到着は全ケースで最初の欠落観測から80 msより前だった。count方策では9ケース中3ケースで先に通知し、elapsed方策では9ケース中0ケースだった。両方策とも9/9でE4→E5を正しく受理した。count側の先行通知は、その回数契約への違反ではない。

末尾E6の追加はE4欠落/E5先頭のタイマーをリセットせず、E4/E5の実進行後に現れたE6欠落/E7先頭では新しい状態に切り替わった。全ケースの独立再構成で、欠落飛越し、未受理pendingの削除、暗黙ACK前進、通知による権限獲得はなかった。明示ACKは登録どおり`new_gap`の実進行後だけ実行した。

## 未検証と停止理由

80 msは診断用固定値で、推奨defaultではない。worker内タイマーは永続化されず、再起動・電源断・suspend・分散時計・複数producer・実モデル消費・token/速度改善・製品完成は未検証。元のSQLiteモデルが保持するのはイベントidentityとpayload digestであり、一般的なpayload回復性も立証していない。

GitHub MCPの公開48操作は読取り専用で、追加の書込み経路も利用できなかった。ローカルにgh/dockerはなく、GitHub直接通信はDNS失敗。したがってsuccessor Issue作成、公開、PR、merge、remote branch削除は **BLOCKED_TOOL_WRITE_UNAVAILABLE**。本セッションによるmain変更なし。これは科学的FAILとは別の配送上の停止である。`SUCCESSOR_ISSUE_DRAFT.md`と`PR_DRAFT.md`は草案であってGitHub上の実体ではない。
