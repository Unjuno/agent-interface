# R567: shutdown Event candidate, not adopted

On base `0ad05fb830c`, a candidate marks shutdown before MCP worker drain and checks the Event after owner startup and before non-close RPC send. The public observe r566 regression plus admitted-send and manual-close controls each passed in normal and optimized pinned isolated Docker runs, three per run; raw conditions, exact candidate diff and outputs are archived. A separate earlier normal `test_mcp_owned_process` run passed 49 tests (raw not retained). The public test additionally checked the child had exited and UNKNOWN was set, but did not independently log absence of child RPC receipt.

Independent static Astra review found the check and send are not atomic; a post-check stall can still cross shutdown. A call after shutdown can start a previously unopened child before the check, and direct `get`/startup bypasses it. Retirement in the rejected caller can race close/cancel and may overwrite evidence; already accepted calls and post-dispatch inspection can be interrupted. The public test accepts any non-observed error and does not prove zero child-side requests. Parent death, permanent spawn stalls, X input release and task effects remain unhandled. This candidate was discarded, and results do not establish recovery or production safety. The r566 and direct-start regressions remain red on the restored base.
