# Calc model-grounding economics pilot

Two separate fresh WSLc Calc allocations compare a single real model grounding followed by local compiled continuation (c04) with a scripted route that makes a second fresh-image grounding call before saving (c05). Both start with the same blank FODS, use `gpt-6.1-sol` low, click the first model-selected A1 point, enter 731 and 864, and independently inspect the saved file. Both validate model-proposed Save coordinates against fixed reviewed bounds, but invoke Ctrl+S through a fixed stable anchor rather than clicking that coordinate. The second model result serves as a validated gate; this is not a free-form agent deciding the entire workflow.

Cached input and reasoning output are subsets of the respective totals and were zero in these recorded calls. The single compiled sample used 50.03% fewer input-plus-output tokens than the single fresh sample; the extra image call is deliberately part of the fresh route. The phase clock starts after the initial model call and A1 click, includes the second model call in c05, and excludes both arms' initial grounding, startup and cleanup. These are descriptive observations, not a full end-to-end latency or price comparison. Provider-reported per-turn usage, request and image digests, unique call IDs and raw returned grounding are in the archives; protocol journals stay local with hashes retained.

Both file snapshots contain the independently parsed cell values and both routes verified releases for every recorded input. The compiled graph itself reports `TASK_SUCCEEDED` using the saved-file verifier; the scripted route has an independent post-run file score rather than that graph verdict. The routes are not proven safety-equivalent: compiled uses its existing semantic guard and graph; the scripted route uses a local filled-pixel guard, and its direct bridge calls did not set the owner's dispatch flag (its close therefore did not attempt another release). The release receipts for its click, entry and save were separately verified. There is no induced stale target or fault, warm reuse series, model-driven planning baseline, randomization, replication, latency distribution, full cost accounting, second workload, or safety-equivalence claim. Treat the comparison as a feasibility pilot, not completion of Issue #3311 or general performance proof.

The comparison arms c04 and c05 were prepared together before their calls. Earlier c01 failed before a model request because Windows Python 3.11 lacked the bounded app-server runtime; c03 failed before a model request because the WSL path converter was unavailable on Windows. c02 was prepared but not run after the host fix. All are retained, including failure records; no partial-input trial was replayed. The Windows host uses Python 3.13 and a Windows-native path converter; the containers use the pinned image, no network, one CPU, fresh independent fixtures, and current main runtime at `184d20ac2adb0128bae7d0d4342c428ae19b8155`. Runtime and host source manifests retain hashes (host source was verified against 2,033 existing file hashes).

`python audit.py` checks the model result/usage/image associations, fixture and script hashes, exact cells, operation releases, compiled receipt, model call counts, and the two setup failures. The archives contain inputs, scripts, top-level outputs, model call results and images; private nested protocol and owner journals are represented by SHA-256 and size, with full local copies preserved.
