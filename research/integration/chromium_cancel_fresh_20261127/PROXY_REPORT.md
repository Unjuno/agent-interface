# Chromium delayed-transport counterexample

This separate preregistered single attempt used source `3c25647af205dd9f3d9a01b87ffed64a24b93132`, two real Chromium windows with separate profiles and a local HTTP effect oracle, in a private user/mount/network/PID namespace with private Xvfb. The old public MCP owner connected through the existing X11 TCP proxy; the new owner used the private Unix display directly. The proxy held the runtime-tracked second `a` press for 3,000 ms, including after the old client closed. The prestarted cleanup supervisor was disabled for this relay condition. This deliberately constructed proxy fault is not evidence about ordinary network frequency.

**The preregistered task oracle failed.** The HTTP fixture first observed exactly `old=a`, then the fresh window produced `fresh=c`; after that it recorded an additional `fresh=ca`. The proxy recorded forwarding the held 76 bytes at monotonic `283059462556304` ns after seeing the old client EOF. The extra fresh effect arrived at `283059464733026` ns. This ordering and the tracked request marker are consistent with the delayed old `a` contaminating the new window. Keymap reads were neutral after cancellation, at 8,506.637 ms, and before fixture cleanup; neutral key state did not imply an uncontaminated task.

The old cancellation completed at `283057178086284` ns with `cleanup_status=UNKNOWN`, `release_confirmed=false`, `late_server_request_possible=true`, and replay denied. Its disconnect observation was unknown and its close returned `cleanup_failed`. The fresh input initially completed and its close was verified, but that does not make the fresh task successful: the later extra effect violated the exact-count/value oracle. The two browser leader processes exited with code 0; the private namespace was torn down after fixture cleanup. No general claim about browser descendants, natural network behavior, arbitrary sites, stdio transport, models, or performance follows.
