# Old owned X-server retirement after UNKNOWN cancellation

One preregistered, no-model attempt used source 5bde5a661628011a0f49d043652314ab615779e1. It ran two real Chromium local-app windows on distinct private Xvfb servers. On the old display, a TCP relay held the runtime-tracked second a request for 3,000 ms across client EOF. After cancellation returned terminal UNKNOWN, the fixture verified the old Xvfb PID (/usr/bin/Xvfb, direct child in the private PID namespace, matching /tmp/.X88-lock), signaled that process via pidfd, and observed its exit before the held-delivery outcome. A fresh public MCP owner and Chromium task then ran on separate display :90.

The old cancellation remained UNKNOWN, release_confirmed=false, and late_server_request_possible=true; its input-obligation snapshot still listed a. After the old X server exited, an independent observer could no longer query the old keymap, recorded as unavailable. The proxy later attempted to deliver the held bytes and got OSError(9, Bad file descriptor). The loopback HTTP oracle saw exactly one old a effect and one fresh c effect through 8,503 ms after cancellation; the fresh keymap was neutral. Fresh close reported verified release. Old close reported cleanup_failed, with no release attempt because the old owner disconnect was unconfirmed.

OWNED_X_CONTAINMENT_OBSERVED means only that the preregistered fixture ordering/oracles passed. It shows that terminating this experiment-owned X server blocked the delayed bytes from producing another observed task effect in this attempt, while a fresh isolated display continued. Termination destroys access to old app state and makes old input state unobservable; it is not verified key-up release, task recovery, or safe migration. The shutdown was manually scripted in the test fixture, not an integrated automatic recovery feature. One forced attempt provides no failure rate or general guarantee. No model calls, outside network, user desktop or downloaded runtime were used.
