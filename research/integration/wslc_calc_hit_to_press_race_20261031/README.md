# WSLc Calc: hit-check to button-press race

Two fresh isolated WSLc allocations used a fixed reviewed A1 point, known blank Calc fixture, main-equivalent runtime f049d928a7a20c36bd7dca8f6133a33874b13889, pinned Calc image, one CPU, 1 GiB, no network and a 60-second timeout. No model calls. Each used the research input-guard child-chain callback from #9861. A test hook simulated another client mapping a transparent InputOnly overlay after the `before_press` callback returned and before XTEST button press; the overlay subscribed to button events. Both runners intentionally stopped after the single controlled click attempt and exited 1.

- A01: all initial hit checks passed. The later diagnostic check saw the overlay but was configured not to reject. The click completed and the overlay received button-1 press and release; input release was verified and final keys/buttons were neutral. This reproduces an input-routing race for the earlier caller-side check in this controlled schedule.
- A02: the same injection and a test-only later hit-chain check configured to reject caused execution_failed before the controlled press; one earlier pointer-motion emission was recorded, release was verified, and the overlay observed no button events. The runtime conservatively records the failed operation effect as unknown. Final keys/buttons were neutral.

An aggregate audit checked the stages, target-excluding late chain, event streams and releases. Both frozen input manifests and 305 runtime hashes matched; containers were absent and ZIP integrity passed. The later fence is a research hook, not a production change or an atomic guarantee: an overlay may still appear after that later query, and X11 queries here have no bounded worker isolation. This controlled test does not prove absence of all side effects, security against arbitrary clients, other windowing systems, model behavior or task completion.
