# New-generation hold interposed during normal cancellation cleanup

One private WSLc/Xvfb allocation uses the same local r132 runtime and lightweight entry as r142. A guarded action held `a` and a fixture queued delayed `b`; the normal `cancel_guarded` path retired the old owner and confirmed its PID-qualified X client disconnect. A test wrapper immediately before the runtime's actual `_release_retired_owner_inputs` call released the old `a` with the fixture, then a separate X connection pressed `a` for a simulated new client. The wrapper then invoked the original runtime release method. This creates an adversarial ordering deliberately; no assertion is made that it arose spontaneously.

The independent keymap showed old `a` up, new `a` down immediately before the runtime release, and `a` up afterward. The target recorded press/release/press/release for `a`, with no `b`; at the post-delay horizon the tested keys were up. The normal cancellation response reported old process retired, disconnect confirmed, and the release worker `readback_verified` despite removing the new hold. The old task/cleanup remained UNKNOWN and replay was prohibited. The private display was destroyed after the test; no physical desktop was touched.

This strengthens r143: an actual normal cancellation cleanup, under an injected cross-generation interleaving, can disturb a newer same-display key hold. It does not establish that a production admission path allows that interleaving, nor its frequency or a general failure of the intended private-display boundary. r142 is a separate no-interposition trial, not a randomized comparison. Source, conditions, raw events, receipts, and runner are retained locally; one attempt, no MAP01 or broad reliability claim.
