# Isolated WSLc Xvfb: server grab, competing map and crash custody

Five fresh WSLc allocations used a synthetic private Xvfb, pinned Calc image only as a pre-existing Python/X11 environment, one CPU, 1 GiB, no network and a 30-second outer timeout. No real desktop, Calc window, runtime implementation or model was used. This research follows the hit-check/press race in #9862.

- A01: after confirming a synthetic target at the point, one X connection grabbed the server. A second connection queued an InputOnly overlay map. The grab owner rechecked the point and sent button-1 press and release; the target received both, the overlay none. After ungrab the overlay became the point's child; final button state was neutral. The one observed grab duration was 0.302 ms, not a performance distribution.
- A02: a separate child confirmed server grab; another connection's probe remained blocked for 0.5 seconds. After the holder was SIGKILLed, the probe completed successfully. It did not hold an input.
- A03 and A04: without a grab, the overlay was mapped and synchronized before the same press/release pair, and received both events while the target received none. A03's raw result keys inherited grab labels from the reused runner even though its conditions and code specify no grab; A04 repeats the control with corrected labels. Both are retained.
- A05: the grab owner pressed button 1 and was then SIGKILLed. The server resumed, but button 1 remained down. A separate surviving client sent release and verified the button no longer down. This is explicit external cleanup in a synthetic X server, not automatic production recovery.

An aggregate audit checks event recipients, request ordering, blocked probe, owner death and surviving-client release. All input hashes matched, containers were absent, and ZIP integrity passed. These single controlled observations do not prove a general atomic runtime primitive: a global X server grab stalls other clients, the holder may hang indefinitely without an independently enforced deadline, X server failure and release custody are separate, and an app cannot process its own requests while held. Pointer grabs, shaped windows, process/window identity, remote X, Wayland/Windows, real applications and integration with existing cancellation/supervisor mechanisms remain untested. No production code changed and no end-to-end task or performance claim follows.
