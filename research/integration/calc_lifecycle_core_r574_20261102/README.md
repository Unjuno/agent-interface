# Experimental Calc lifecycle orchestration core

This is an incomplete, injectable orchestration prototype for the planned real-Calc comparison. It has no WSLc driver, Windows process-tree ownership, real scorer, GUI or model configuration. Do not use it to run live cells. Its caller/driver is trusted to implement identity tokens and its claimed audit and release receipts; mock results are not evidence of actual cleanup, input release, correctness or speed.

The core creates a fresh allocation directory, persists conditions, starts and waits through a driver, independently attempts host/container cleanup, separately records audit/release/cleanup, and marks a late zero exit incomplete. Execution and cleanup have separate budgets; a synchronous driver that blocks indefinitely can exceed them, and audit is not yet bounded. `before_result_write_ns` explicitly excludes final result serialization/write. Startup token preparation currently exists only in memory, not in a durable pre-spawn ownership protocol. Abrupt process death, conditions/result write failure, subprocess descendants, exact-CID binding, and partial-start reconciliation need a real design and tests before use.

Run the local fake-driver checks with:

```
python -m unittest discover -s research/integration/calc_lifecycle_core_r574_20261102 -p test_lifecycle_launcher.py -v
python -O -m unittest discover -s research/integration/calc_lifecycle_core_r574_20261102 -p test_lifecycle_launcher.py -v
```

No live allocation, model call, WSLc container or GUI was run for this prototype. The existing benchmark evidence and limits remain in `../calc_interval_scorecard_r572_20261102/`. The goal remains full measured task/release/recovery comparison, not completion of this helper.

The core checks a single execution deadline after the container wait and gives host/container cleanup a separate shared budget. It records late cleanup and refuses overall success, but synchronous start, cleanup and audit methods can still block beyond their budget; this is not a hard wall-clock bound. Driver return values are only minimally checked, and a driver-provided `release_confirmed` is trusted rather than independently authenticated. A concrete driver must persist ownership before resource creation, capture exact commands and raw diagnostics, validate CID/run identity, own the host process tree, supply bounded operations and an independent scorer, and distinguish absence from transport errors. No such driver exists here.

### Experimental exact-CID cleanup helper

`wslc_cleanup.py` is a standalone research helper, not a driver wired into `run_attempt` and not approved for live GUI/input use. It requires a caller-provided complete CID and unique `agent-interface.run-id` label. It checks the inspect identity and label and a full-ID positive listing before attempting a bounded stop; command output is retained as base64 in the returned receipt. Missing, malformed, timed-out or failing observations remain `UNKNOWN`. `observed_absent` means only that one successful exact-ID list was empty after a successful stop; it does not establish input release, task effect, process-tree termination, or general filter correctness. The caller must securely persist and redact receipts because inspect output may contain environment and mount data. The helper does not handle a partial or delayed CID file, a failed launch without a known CID, crashed Python process, host custody, or cleanup after its own deadline. Synchronous process creation and system calls are not independently proven bounded. Its fake-runner tests are not live WSLc evidence.

The helper optionally accepts a new, exclusively created JSONL journal path. It flushes and fsyncs command intent before invocation and command output after return; a Python-level interruption records its exception type when the filesystem permits. A missing return event means the command outcome is unknown. This is not a crash-proof independent custodian: process termination or storage failure can interrupt any write, and fsync or process creation can exceed the deadline. Journals include unredacted inspect output. A verified existing container reported stopped by inspect and present in the ID list produces `observed_stopped`; it is not proof of absence, release, or process-tree retirement. Automatically removed or otherwise missing containers remain UNKNOWN. The live launcher must require its own persisted identity and journal and must not equate either status with `confirmed` cleanup.

The experimental `remove_exited=True` mode requires a fresh exclusive journal. It accepts only an exact CID and label, inspect `Running=false`, `Status=exited` with integer exit code, and a matching full-ID list row with `State=exited`. It syncs the observed exit code before non-forced removal, then checks a separate empty exact-ID list. The exit observation and removal outcome are distinct; an UNKNOWN result can still carry a prior observed exit code. The mode does not stop running containers, does not delete volumes, and does not establish input release. A concurrent restart between observations remains possible; the exit code is an observation, not a guarantee of uninterrupted state. This mode currently has fake-runner tests only; R579 exercised the underlying WSLc commands separately, not this code. Journal and inspect data may contain secrets. This remains disconnected from the Calc launcher and has no independent post-crash custodian.

### Experimental deadline recovery follow-up

`recovery.reconcile_owned` tries the existing identity-checking stop helper and then separately invokes its non-force exited-removal mode, each with its own journal. An ordinary exception during stop does not itself suppress the second observation; no receipt is promoted to task success. Both calls share one advisory budget: if stop exhausts it, remove is not attempted, and late receipts are marked. Fixed journal names make this a one-shot allocation; use a new allocation for any later reconciliation. A synchronous helper may exceed its budget, final fsync may block, and a Python-level interrupt is re-raised after the second attempt, so the caller must preserve aggregate evidence separately. This is not a parent-independent custodian or production driver.\n
`calc_smoke_payload.py` is a corrected research candidate derived from the R581 historical payload: an exception after window observation changes the final status to error, and child process output is retained to local container logs. The fake-environment regression checks that this ordering exits nonzero. It still has no independently bounded teardown and has not been run on real WSLc. Historical experiment files remain unchanged.

`wslc_driver.ContainerDriver` is a one-attempt research container adapter. It persists a run label and exact command before spawn, retains local raw command events, matches the complete CID file against launch output, verifies inspect ID/label, and reports exit status separately from cleanup. Its optional mounts restrict destinations; `/src` and `/in` must be read-only. Cleanup uses the same injected transport and the two-stage reconciler. A partial launch with no complete CID remains UNKNOWN and requires external reconciliation; the caller must always attempt cleanup in `finally` and must not create another attempt as though absence were proven. A start reported UNKNOWN cannot become a successful wait. Logs contain unredacted host paths and environment data. Budgets are per-operation and synchronous fsync/process creation can exceed them. This is not an independent supervisor, a model-host process tree owner, an input-release verifier, or a production driver; artifacts must be captured and scored before cleanup removes an exited container. A scoped actual no-GUI/no-input sample is recorded in `../wslc_container_driver_r584_20261102/`.

`win_job_spawn.AtomicJobProcess` is a Windows-only, single-thread research prototype. It creates a private kill-on-close Job and uses `PROC_THREAD_ATTRIBUTE_JOB_LIST` to place the new process in that Job as part of CreateProcess, initially suspended. Membership must be confirmed before resume. Construction and start are separate so the caller retains the owner after start failure; unconfirmed membership uses the retained exact process HANDLE for termination, and failed handle closes remain available for retry. Optional experimental stdio uses a handle allow-list; it is not a production pipe lifecycle or model integration and has no concurrency protection. The scoped direct-child owner-death experiment is `../win_job_atomic_parent_r590_20261102/`; do not infer general parent-death recovery, input release or WSLc cleanup from it.

The optional stdio experiment is documented in `../win_job_stdio_r592_r593_20261102/`: the initial EOF test was invalid and is preserved alongside a corrected worker-exits-before-grandchild test. Parent streams must not be closed underneath a blocked reader; reader join and stream closure require separate evidence. Python FD ownership-transfer interruption and other threads concurrently spawning inheriting processes remain unresolved, so do not use this prototype as the model host.

`job_host.JobHost` is an experimental outer process wrapper, not yet connected to the Codex client or model. It starts two binary drain readers before resume, does not accumulate unbounded output in memory, and separates process exit from Job/reader/stream retirement. Late wait and cleanup observations remain UNKNOWN. `../win_job_host_drain_r595_r598_20261102/` retains the test histories, including the initially inadequate deadline test and EOF type correction. File I/O, CreateProcess, fsync, and reader shutdown may block beyond the advisory budget. A reader whose thread start is ambiguous is retained as UNKNOWN; concurrent spawn, ownership transfer interrupted by asynchronous exceptions, output limits, parent death during start and full descendant HANDLE audit remain open. Never treat `closed_scoped` as proof of model task success or WSLc cleanup.

Reader startup distinguishes `not_attempted`, `started`, and `unknown`. Before `Thread.start()` is invoked, startup has not been attempted; after entering it, any exception remains UNKNOWN because native thread creation can precede publication of `ident` and the started event. A joined reader permits parent stream closure, but does not turn an uncertain start into success. `close()` can be retried on the same JobHost while process handles or readers remain observable; an unknown reader with no published identity cannot be joined here, so its parent streams remain open and the attempt allocation must stay quarantined. Continue independent work in a fresh exclusive allocation rather than reusing it. Local Windows tests cover failure before the second reader's start method and an exception after underlying thread creation, alongside the existing JobHost, process-spawn, and stdio cases (25 passed on 2026-11-03). Native thread-creation failure versus interruption immediately after creation is still not discriminated by this wrapper.
