# WSLc ViZDoom startup failure and diagnostics

A01 was one predeclared WSLc successor of the Docker R46 owned-target retirement cell at experimental PR #9814 head f212e1610cbafd719dece36fbd0d07a63f17274b, not current-main production code. It failed with `old game window unavailable` before any measured cancellation, isolation or task-effect gates. Output and failure remain unchanged. WSLc image ID differs from the Docker source image despite matching rootfs layer lists; details are in A01 conditions and the WSLc evidence merged in PR #9817.

A02 started the same game executable under a private unauthenticated Xvfb, held it for four seconds and captured output; it remained alive until the diagnostic ended it. A03 repeated startup with the failed runner's Xvfb authentication and listen options; it too remained alive. A04 used those options and observed a mapped ViZDoom window after two seconds. These startup diagnostics launch the game directly with subprocess, not OwnedTargetProcess or MCP, and differ from A01 in startup sequence and observation. Therefore they do not establish the cause of A01 or validate recovery. No input was injected and no live attempt was rerun.

All four exact-container-ID cleanup queries returned exit 0 and no match. The four conditions, output, failure, cleanup records and hashes are preserved. This is not a MAP01 completion, WSLc task-control success, performance comparison, or reliability estimate.

A05 reproduced the startup failure using OwnedTargetProcess with target stdout/stderr captured: the child exited 255 and stderr reported it could not create `./_vizdoom/` on the read-only filesystem. A06 changed only the target cwd to a writable temporary directory; the child remained alive and a mapped ViZDoom window was observed after about 223 ms. Both are one no-input diagnostic each and preserve their own outputs and cleanup results. This isolates a concrete startup configuration cause under these schedules; it does not retroactively pass A01 or establish full recovery.

A07 is one predeclared WSLc successor to failed A01, using the same experimental source but a runner changed to run from a disposable writable temporary directory. Its 18 gates passed and eleven additional checks in `a07/audit.json` passed. Old owned ViZDoom exited; the original operation remains runtime_failed/UNKNOWN/no replay; the old Xvfb was manually retired and a new same-number authenticated server started. The fresh DoomGame-managed target moved 153.4049835205078 map units with MCP W versus 0 coast. XRecord covered the old delayed-input horizon, saw W down/up and no B before horizon, with a later B positive control. Fresh close was verified and the exact container ID was absent after exit. All data, including 58 hashed files, is retained.

This fixed-order single case is not a general reliability, display-custody enforcement, hard deadline or MAP01 completion result. Fresh target creation and server replacement are manual and the fresh target is not pidfd-owned. XRecord device events cannot prove per-client delivery or absence of recording loss; the old task outcome remains UNKNOWN. The loaded WSLc image ID and configuration differ from its Docker source.
