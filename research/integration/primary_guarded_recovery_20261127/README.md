# Primary caller: explicit release after a controlled X11 failure

Three isolated zero-model trials used Docker with private Xvfb, no network, one CPU and a 1 GiB memory limit. A synthetic X11 window received a checkerboard observation and a guarded keyboard action. The Node primary stdio caller used the real relay implementation and MCP server, with a test-only server wrapper redirecting relay startup and injecting the existing one-shot fault factory.

- `startup-refusal.zip` records a test-harness startup failure before input: the initial server script lacked a multiprocessing entry guard, so the owned process timed out. The independent key readback reported the selected key up. This is a failed setup, not a passed recovery test.
- `controlled-recovery.zip` records the corrected, separately registered trial. The fault raises after the `b` key-down reaches X11 and fails the first automatic release. The original input receipt reports `execution_failed` and `recovery_required=true`; independent X readback and the app event loop show the key down and a press. The Node caller explicitly invokes recovery on the same revision; the original recovery receipt reports verified empty tracked input and independent readback and app events show the matching release. A subsequent request to resend the old input is rejected while the caller remains stopped, followed by explicit close.

- `validated-revision-recovery.zip` is a new, separately registered repeat after fixing an unstable JavaScript getter that could change the recovery revision between validation and transmission. It exercised the revised caller blob `32480a4cb8def43cd52d0bf5baef46a5f4687149`, matching PR head `df8d63dd4b084c5ec95c752c18ead8757d640146`. Independent X readback again observed the key down before and up after recovery, with press/release events and refusal to replay. The getter regression failed before the fix and passed after it.

`audit.py` validates each archive and internal seal, the registered input bytes, the tested primary caller's Git blob, input and recovery receipts, independent key-state readings and event order, and the replay refusal. Run `python audit.py`. Archive digests are pinned inside the auditor. The registration preserves hashes of 394 server source files, but these external source files are not bundled and the archive audit cannot independently reconstruct their full contents; the tested recovery caller blob `b711066bdda408f4f12ecb4466e07992e6875ba1` matches PR #10592 at the experiment's recorded head `aa8038759df06e1b4fc7ba3d228e812a4bb9bdf5`. The test factory file matched main `d0aabf07d5d58cf36347e6e54eff58433f2b674d` at blob `31cba573f41fef7b9ca77921a742e00cfea1b3d1`; the server was a separately registered synthetic snapshot, not an official release.

This single controlled event does not demonstrate model-driven operation, arbitrary crash recovery, a real application task effect after recovery, fresh-owner continuation, or WSLc/native Windows. The recovery action only releases tracked inputs; it does not determine the effect of the failed action or authorize replay.
