# Delayed XTEST request across guarded-owner retirement

This WSLc experiment extends the [child-authority cleanup pair](../wslc_cleanup_child_authority_20261101/README.md). An actual spawned guarded owner sent `a` to an independent target. In the first arm a test hook also sent a delayed XTEST `b` press on the same owner connection with an 8,000 ms delay and flushed the connection; in the second it withheld `b` and paused the owner in test code. Both arms stopped the private Xvfb after the old `a` was observed down, began actual cancellation, and resumed the server after the prestarted cleanup worker entered. The worker's release readback and an independent keymap showed `a` up; the old result remained `UNKNOWN`, release unconfirmed at product level, and replay disallowed.

| Arm | Observed `b` presses at old target through 9 s after marker | `b` state at horizon | Fresh guarded task |
| --- | ---: | --- | --- |
| Delayed request, owner retired | 0 | up | separate target received `a`; release verified |
| Withheld request, owner retired | 0 | up | same |
| Positive control, owner kept alive through horizon | 1, approximately 8 s after marker | down, then fixture released | same after old owner retirement |

The marker in the delayed arm establishes that the client issued and flushed the request; it does not by itself prove when the server accepted or queued it. The positive control demonstrates that the injected request can reach the target when the owner is kept alive, but it did not stop or cancel the server and had global autorepeat disabled; the retired pair had the default setting. The positive control's old call did not yield a successful task result: after fixture cleanup its owner was retired and cleanup remained `UNKNOWN`. These differences, fixed order, and one attempt per arm limit attribution. The old target's event log and a single horizon keymap do not prove that no transient `b` was delivered elsewhere or that arbitrary server queues are drained. The result supports only the observed private-Xvfb boundary, not a general replay or release guarantee.

Two failed positive-control attempts are retained. `positive-r01` did record `b` but failed because the runner required the old action thread to complete before observing the horizon. `positive-s01` failed when it read a partially written marker. The final `positive-t01` used atomic marker publication and observed the event and key state before retiring the old owner. Neither failure is converted into a pass.

The frozen mixed source uses main `e5925b6bd99fd4ff3f8e0bda5ed4d7cc02d92c4d`; the owner, cancellation supervisor and private-display module match draft [#10088](https://github.com/Unjuno/agent-interface/pull/10088) `926ba07214b5ab53ff38f66af5c0947606850118`, while other files come from [#10074](https://github.com/Unjuno/agent-interface/pull/10074) `0675ab810f7ee890d0904b8a402678c81f8dbafb`. The exact mixed snapshots are retained. All cells used pinned image `sha256:6150a4f3c779a51b3ac6a7d93bc1d0450803325efb7ab38ade8b1aaf79c33e25`, one CPU, 1 GiB memory limit, no network and no pull; WSLc reported swap was not limited.

[raw.zip](raw.zip), SHA-256 `ac66f040d5c8b900d745a830f70e8216341dcbf00a930cc139271496c3efede3`, contains all five frozen conditions, sources, logs, target events and receipts, including both failures. Ephemeral authority files are excluded and the archive was checked for their key bytes. The audit verifies source hashes, event timing, target observations, key states, cleanup statuses and fresh task releases. This is not proof of natural-failure behavior, automatic display replacement, old-task success, production MCP integration, hard deadlines, MAP01 completion or a general reliability rate.
