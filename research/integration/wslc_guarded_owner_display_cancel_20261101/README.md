# Guarded old input, uncertain cancellation and owned display replacement

This WSLc test-harness composition advances the earlier [fixture-held input comparison](../wslc_owned_display_current_revision_20261101/README.md). A spawned guarded owner sent `a` to an independent old Xvfb target. A test-only hook synchronized that press to the server and paused the child before the input call returned. The target recorded `a` and an independent X client saw the key down. The harness stopped the privately owned display, invoked real guarded cancellation with a four-second transaction deadline, and then either retired/replaced the display or resumed it as a control. This pause is injected; it is not a naturally stalled X request.

Both cancellation results reported `cleanup_status=UNKNOWN`, `release_confirmed=false`, `replay_allowed=false`, an old input obligation for `a`, and retired owner process; the old guarded call ended with `EOFError`. **The same cancellation responses also reported `input_dispatched=false`, despite the target's recorded press and the independently observed down state before cancellation.** This contradicts interpreting that field as proof that no input was sent in this case. The inconsistency remains unresolved and neither arm establishes successful recovery of the old operation.

In the replacement arm the draft `PrivateDisplayOwner` retired the stopped Xvfb; a new owned display started neutral. A fresh client held `b`, an intentionally injected old-connection `b` release failed with `ConnectionClosedError`, and the fresh hold survived until a fixture released it. A fresh spawned guarded owner then typed `a` into a separate target, which recorded press and release; guarded release and final neutral X state were verified. Destroying the old display caused its target to exit with code 1 and discarded its application context.

In the same-display control, after server resume the old `a` remained down and required a fixture release. The old target's retained value changed from `a` before stop to `aaa` by the end, with two additional `a` presses recorded after resume; their cause was not isolated. The old connection's deliberately injected `b` release cleared a fresh client's `b` hold. The fresh target subsequently recorded one `a` from a fresh guarded task and its release, with neutral final X state. The extra old-target presses and the inconsistent negative dispatch field are important counterevidence, not a successful old-task oracle.

The two fixed-order allocations used main `a2577208ef2bda3287aa687becad88d0a71aa149`, `PrivateDisplayOwner` source at [#10088](https://github.com/Unjuno/agent-interface/pull/10088) `93ef7f4321b94ef83cdbea472cba7e85f51cfb78`, and the guarded-owner snapshot from [#10074](https://github.com/Unjuno/agent-interface/pull/10074) `0675ab810f7ee890d0904b8a402678c81f8dbafb`; the mixed source tree is retained rather than presented as one commit. The pinned image was `sha256:6150a4f3c779a51b3ac6a7d93bc1d0450803325efb7ab38ade8b1aaf79c33e25`, with one CPU, 1 GiB memory limit, no network and no pull; WSLc reported swap was not limited. Both launchers returned zero on the frozen fixture criteria, which did not require old-task success or a consistent dispatch field.

[raw.zip](raw.zip), SHA-256 `b25f688f9c4ad6b4684192de9c28cc1337650624791b22812a2cc6f30a102268`, preserves frozen source, conditions, logs and receipts; ephemeral authority files are excluded. The audit checks hashes, actual old press, cancellation UNKNOWN/obligation/no replay, exact old target values, new key states, target event order and process exits. The ownership primitive is orchestrated by the test harness, not wired into production cancellation. Neither this single pair nor its injected stale release proves queued-request fencing, same-number authentication isolation, a hard deadline, physical old input release, preserved old task effect, MAP01 completion or general reliability.
