**Strict outcome: FAIL_OR_UNKNOWN (18/20).** One fresh current-main native fixture held the injected Q-down callback for a planned 1250 ms. The measured hold ended 1245.455 ms after it started; the callback returned 0.124 ms later. All 20 exact-call polls remained pending and release-unconfirmed while the callback was retained. The independent same-generation Q-state sample was neutral, but it is not evidence that the Q-up traveled through the blocked hook. The traced Q-up (`VK_Q`, key-up) was sent and returned after callback return.

The process-tagged trace captured the recovery helper process, `_recover`, `release_all`, and `Win32Backend._send`. `release_all` entered 4.500 ms after cancel start and returned 1261.697 ms later, after callback return. Twelve Unicode compensating key-up SendInput calls were recorded. The first four each spent 312.991, 313.831, 312.903, and 298.876 ms inside the wrapper; the fourth interval crossed callback return. The remaining Unicode key-up sends were sub-millisecond. These intervals are consistent with the blocked hook delaying native injection, but this single run does not prove kernel causality or physical application time. The Q key-up itself completed about 8.294 ms after callback return.
