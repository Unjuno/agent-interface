# R569: simulated pending retirement enters prestarted cleanup cache

On draft base `b17cc87f4b0`, one direct fake-owner unit characterization ran normally and with Python -O in pinned isolated Docker Linux. A synthetic `{retired:false,status:retirement_in_progress}` passed to `_cleanup_after_owner_retirement` produced an `owner_not_retired`/`not_attempted` pair. When a later `{retired:true}` was passed to the same object, the cached pair was returned: the mocked live obligation reader and supervisor were not invoked. A separate otherwise equivalent control given only `{retired:true}` invoked its mocked supervisor and returned the mock's release receipt. Both runs exited 0; conditions, exact test and output are in raw.zip.

The pending status was introduced only by the discarded r568 candidate; this experiment injects it and does not prove natural reachability in current main. It does not establish that a later release would be safe: an old release can affect a newer client's hold, so display-generation fencing and custody matter. Mocks do not demonstrate real disconnect, input release, task effect, WSLc or recovery. The characterization test was not retained as a normative invariant; it describes current cache behavior, which a justified future transaction design may change.
