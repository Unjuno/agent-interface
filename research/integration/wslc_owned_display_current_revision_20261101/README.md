# Current private-display draft: held-key composition check

This is a new, fixed-order WSLc pair repeating the earlier [test-harness composition](../wslc_owned_display_composition_20261101/README.md) with the `PrivateDisplayOwner` source at draft [#10088](https://github.com/Unjuno/agent-interface/pull/10088) head `93ef7f4321b94ef83cdbea472cba7e85f51cfb78`. The owner was combined in the harness with the guarded-owner source snapshot used by the earlier experiment; that mixed tree is preserved in the archive and is not claimed to be the complete source of the draft commit. Main was `a2577208ef2bda3287aa687becad88d0a71aa149` at preparation.

A fixture pressed and held `a` on an owned private Xvfb, then stopped it. One arm retired the server and launched a different owned display; the other resumed the same display and used a fixture release for the old `a`. A fresh client held `b` while the old connection attempted a `b` release. On replacement, the old connection raised `ConnectionClosedError` and `b` remained down; on the same display the old release succeeded and `b` became up. A fixture then released the surviving `b` in the replacement arm. In each arm a fresh spawned guarded owner subsequently typed `a` into a separate target, which recorded press and release; the guarded release was verified and final X input was neutral.

Retiring the old server destroyed its target's application context; that target exited 1. The fresh target exited 0. The resumed control's targets both exited 0, and its fresh target recorded the fixture's old-`a` release before the later task. A neutral replacement is not confirmation of physical release on the old server. The old hold and stale release were deliberately injected by test clients, not by a stalled guarded operation or an already queued request. The display owner is not integrated into cancellation, MCP or replay policy.

Both allocations used pinned image `sha256:6150a4f3c779a51b3ac6a7d93bc1d0450803325efb7ab38ade8b1aaf79c33e25`, one CPU, 1 GiB memory limit, no network and no pull; WSLc reported swap was not limited. Both launchers returned zero. [raw.zip](raw.zip), SHA-256 `3dc8d2e666882feaa776dbd9fe9659f941d214c7ad888551916acc20d588a3bc`, retains frozen source, conditions and receipts; ephemeral X authority files are excluded. The audit checked source hashes, ordering, key states, target events, release receipt and process exits. This one fixed-order pair does not establish same-number cookie fencing, a hard deadline, natural-failure recovery, MAP01 completion or a general reliability rate.
