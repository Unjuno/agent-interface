# R149: native keyboard queue residency past expiry and recovery

Method repair relative to consumed R147: both native ctypes MSG field reads
now use hWnd. R147 crashed on the first preview; its action remains UNKNOWN.
Separate UP-only R148 recovery cleared that durable obligation and fenced both
generations. The native ABI regression fails before this correction and passes
after it. R149 changes this necessary method defect and uses a new target,
nonce and custody snapshot. Timing, decision thresholds and counter criterion
remain unchanged from R147. It is not a replay of the old operation.

Host authorization: the user's existing permission for this PC and native
computer-control experiments. One fresh owned fixture, no Docker/model/runtime
download, no external target. This is a new mechanism relative to retained
r08-r10: keyboard messages remain in the Windows queue, with PM_NOREMOVE
previews only. Non-keyboard messages continue through the ordinary pump. No
fixture-side deferred keyboard list, MSG reconstruction or synthetic keyboard
PostMessage is permitted. Current main and all runner/fixture bytes are frozen
in conditions.json before launch. Prior allocations/results are not replayed.

H: a real accepted A down/up can remain unconsumed in a responsive fixture's
native message queue beyond authority expiry, native neutral recovery and its
two-second sampling horizon, then cause an independent task counter update.
This would show the difference between input-state release and pending app
consumption. It is a deliberately filtered application schedule, not a claim
of spontaneous late OS delivery in arbitrary apps.

T: one public supervised-win32 MCP action on a fresh exact PID/HWND/generation.
The program focuses only that owned window, sends A down, waits 50 ms, sends A
up, then waits 15 s with authority fixed at execution-clock sample +4 s.
Automatic expiry should retire the producer and recover. Record one optional
fallback cancel only if exact-call polling is still nonterminal after 12 s;
poll at most 8 s more. Do not replay a dispatch or restart an uncertain server.
Configure the existing 2,000 ms late-input horizon. After the exact terminal,
hold the queue for a further 650 ms, then permit normal OS dequeue and immediate
TranslateMessage/DispatchMessage. Keep a 500 ms tail after the first effect.
PM_NOREMOVE previews are logged at a bounded cadence and never used to dispatch.
The app's maximum hold is 20 s and lifetime is 180 s. Timeout invalidates the
planned discriminator. Close only the owned fixture, without force, after no
dispatch or after clear native custody and sampled neutral A.

D: record separate checks; all are required for PASS_SCOPED_QUEUED_EFFECT:
1. Fresh provenance, exact target generation, one dispatch, QPC clock and
   unchanged frozen source; same confirmed Codex custody view, initially clear.
2. A down is independently sampled before expiry. An A WM_KEYDOWN is previewed
   without removal before expiry and again after the verified recovery horizon.
3. Exact action is recovered after the submitted expiry, release is confirmed,
   no fallback cancel is used, and the retained 2 s horizon has at least two
   observations, a sufficient end-minus-release interval and no gap over its
   configured 100 ms bound. Preserve UP attempt evidence independently.
4. No keyboard dispatch/task effect occurs while the queue is held. The hold
   resumes by the runner flag, without timeout. The native removed key record
   matches a retained preview (HWND/message/wParam/lParam/OS time), and the
   real WndProc produces exactly one initial A-down task counter increment
   after expiry, horizon end and terminal observation. No copied message is
   used to produce it. There must be no unexpected keyboard key.
5. Independent A samples remain neutral after terminal; the original public
   result keeps task_success null and replay_allowed false before and after
   the effect. Preserve the effect and release as separate observations.
6. Retain raw requests/replies, queue/WndProc/effect events, samples, target
   source/identity, clock, custody before/after, process exit and hashes.

Missing evidence, foreground/generation change, timeout or unconfirmed release
is UNKNOWN/INCONCLUSIVE, never a task-success upgrade. A counter mismatch or
an effect before the required boundary is a failed discriminator. The raw first
outcome remains authoritative; later auditors may only add scoped corrections.

C/U: the fixture deliberately controls consumption; scheduling and logging
perturb timing. A queue preview can process nonqueued Windows messages. GetAsyncKeyState
alone can return zero on failure, so it is not the release proof: use the owned
recovery receipt, target binding and horizon together. No physical 20 ms release
claim, continuous-state claim, MAP01 result, compiled planner result, reliability
rate or same-model performance comparison follows from this single fixture run.
