# MAP01 visual review with and without fixture frame advance

Four fresh WSLc episodes investigate the prior [visual-review timeout](../wslc_map01_hud_visible_effect_20261101). After natural-watch cancellation, verified release, review and a fresh exact 49 HUD cue, each either performs the same separately preplanned 85 ms guarded attack or withholds. During the subsequent cooperative 600 ms visual review, the fixture either calls `game.advance_action(1, True)` before each screenshot or makes no such call. Recognition receives only the screenshots, binding and exact prior 49/48 templates; simulator counters are not supplied to it. The four independent games use the same fixed seed 991040, HUD setting, layout and scripted policy; order was passive/fire, advance/fire, advance/withhold, passive/withhold.

| allocation | follow-up | review fixture | visual result | review frames / fixture advances | simulator ammo after review |
|---|---|---|---|---:|---:|
| ew01 | attack | passive | timeout_unknown | 10 / 0 | 48 |
| ew02 | attack | advance | visual_48 | 2 / 2 | 48 |
| ew03 | withhold | advance | timeout_unknown | 7 / 7 | 49 |
| ew04 | withhold | passive | timeout_unknown | 10 / 0 | 49 |

In ew02 the first visual crop matched 49 and the second matched 48 at 159.653 ms after review start, before the 600 ms decision deadline. The two fixture calls took 25.565 and 24.722 ms. In the three timeout cases all reviewed crops matched 49; the passive fire arm later had an exact 48 final screenshot. All original interrupted actions retain partial-effect unknown. Every follow-up and owner release that was attempted was verified neutral; old aliases were refused without input. The simulator recorded no new hit or kill during ew02's interval, so recognizing ammunition is not proof of task success. The scorer's `sample` helper itself calls `advance_action` and is not a passive independent sensor.

This fixed-order experiment supports the hypothesis that fixture frame advancement changes visibility in this setup, but it does not isolate the precise update mechanism: the calls alter simulator progression and the games are separate. `advance_action` is a privileged simulator API unavailable to an ordinary screenshot-only controller and is not proposed as a production fix. Two modes on one fixed seed, known templates and scripted inputs do not establish a latency bound, general reliability, semantic task effect, model autonomy or MAP01 completion. The 600 ms limit is cooperative; capture/advance calls can overrun. Seed and HUD settings are recorded by launcher/conditions, not independent simulator readback.
