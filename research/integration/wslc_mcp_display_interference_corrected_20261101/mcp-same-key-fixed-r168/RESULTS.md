# Same-display MCP cancellation with corrected single-injection fixture

One fresh private WSLc/Xvfb allocation repeats r150's controlled two-server scenario using the same unmerged r132 runtime candidate, but replaces the repeatedly wrapped fixture with the idempotent version and append-only injection log used in r162. Two independent in-process MCP server objects have distinct real spawned guarded owners on the same display and target. The first owner holds `a`; the test fixture explicitly clears that old hold; the second owner's guarded input then holds `a`. Independent keymap confirms the second hold before first cancellation.

The first server's MCP cancellation reaches a terminal receipt showing its old child retired, PID-qualified disconnect and readback-verified release. Before cancelling the second, independent keymap shows its `a` has changed from down to up; the target records `a` press/release/press/release. Each owner logged exactly one delayed `b` injection. Both original actions returned runtime_failed, both final closes reported cleanup_failed / UNKNOWN, and replay remained prohibited. At a check after both delayed-request flush horizons, a/b/c were up and the target had no b press; that fixed-window observation is not a general queue-drained proof.

This re-observes the r150 same-key interference with fixture multiplicity controlled; it does not retroactively change r150. The order and first release are deliberately injected, the target and display are synthetic and both MCP server objects run in one process through call_tool. One attempt, no spontaneous-frequency, stdio, physical desktop, MAP01 or successful recovery claim. Exact source, conditions, injection logs and raw receipts are retained.
