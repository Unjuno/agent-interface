# Retired X11 owner: cleanup, normal cancellation and generation interference

These are four finite local-candidate WSLc/private-Xvfb records, not evidence of main, physical desktop, MAP01, or overall recovery. The exact runtime files used by all four are preserved in `runtime-source.zip`; the four frozen manifests contain SHA-256 of every source and trial script. `python -B verify.py` checks the archive, scripts and key recorded outcomes. The pinned image, limits, allocation IDs and protocols are in each arm's conditions. `private-command.json` files are omitted because their bind mounts contain local absolute paths; the frozen `run.py` gives the command template. Raw target events, receipts, logs and launcher results remain in the arm directories.

* r137: on an injected prior-retirement race, manual fixture release control passed, while direct helper failed after disconnect supervision timed out. The helper arm remained held and did not run its horizon.
* r141: same runtime with test-only imports moved into the guarded entry point; an explicit private helper released the old held key, then the horizon and a fresh task passed. Old cleanup remained UNKNOWN.
* r142: unmodified normal cancellation retired the owner and automatically obtained a release receipt; keymap was neutral at the horizon and a new task completed. The old task and cleanup remained UNKNOWN and replay disallowed. One run took 419.55 ms; this is not a bound.
* r143: after fixture release of old input, a separate simulated X client pressed the same key. An intentionally invoked stale private helper released the newer hold despite an old-PID disconnect receipt and readback success. This is a dangerous test ordering, not a claim that the normal runtime triggered it.

Each arm is one attempt; delays and, where stated, decision pauses are injected. XRes disconnection is not a queue-drained guarantee, and keymap checks are point observations. r142 does not resolve the prior-retirement race. r143 shows why a stale release cannot be treated as safe merely from a process receipt: new input needs enforceable exclusive custody or equivalent protection. These candidates are not included in #10094. See each `RESULTS.md` for boundaries.
