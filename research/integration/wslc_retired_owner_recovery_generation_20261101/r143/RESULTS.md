# Stale retired-owner cleanup after another X client presses the same key

One fresh private WSLc/Xvfb allocation used the r141 local runtime source and lightweight entry point. In the forced prior-retirement race, the old guarded action held `a`; cancellation returned UNKNOWN, without invoking cleanup. The test fixture deliberately released the old `a`, then a separate X connection injected a new `a` press. An independent connection verified the key was up between generations and down before the next step. The test then **explicitly called a private old-owner cleanup helper** with the old retirement receipt, despite the new client's hold. This intentionally tests a dangerous ordering; it is not a normal public recovery path.

The old PID-qualified disconnect check succeeded and the shared old obligation still named `a`. The old cleanup returned `readback_verified`, but independent keymap showed the new client's `a` had become up. The synthetic target recorded two `a` presses and two releases, with the second release after the old cleanup; its value was `aa`. At the check after the queued delayed-b horizon both keys were up, and the log showed no `b`. Old close stayed UNKNOWN. The private Xvfb was destroyed and WSLc list was empty.

This directly shows a stale cleanup can affect a later same-key XTEST hold in this isolated sample. PID-qualified disconnection and a successful release readback do not themselves establish exclusive ownership of the global X input state. It does not prove the guarded runtime automatically invokes stale cleanup: the candidate deliberately avoids it in this race. The safe design needs enforceable exclusive custody/fencing or an equivalent proof through cleanup, not merely an old process receipt. One sample, synthetic clients, injected race; no physical desktop or MAP01 claim.
