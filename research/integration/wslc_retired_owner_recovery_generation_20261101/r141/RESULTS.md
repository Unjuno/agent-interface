# Explicit retired-owner recovery with a lightweight trial entry point

One new private WSLc/Xvfb allocation repeats the r137 helper scenario with the same runtime source and pinned image. The test-only Xlib, fixture and owner imports were moved inside the guarded main function, so spawned workers no longer re-import the heavy test fixture as part of executing the trial's main module. The frozen source, conditions, commands, and raw outputs are retained here. The r137 manual-release arm provides a previous control, but was run in another allocation with the heavier entry point; this is not a randomized or repeated comparison.

A guarded action actually held `a` while a fixture queued an 8-second delayed `b`; a real `cancel_requested` acknowledgement was received and the parent deliberately paused the decision, retired the child, and resumed. The candidate returned `cancel_unconfirmed`, UNKNOWN, with no automatic cleanup; the independent X client observed `a` still down. The test then explicitly invoked the existing private cleanup helper on the retired owner, while no new owner existed and the private display was isolated. It obtained a PID-qualified disconnect receipt (53.77 ms), read the retired child's shared obligation for `a`, and obtained a release readback receipt (366.63 ms). Independent keymap then showed `a` and `b` up, and remained up when checked after 8.5 seconds from delayed-request flush. The target event log contains no `b`; a fresh owner subsequently typed `a`, bringing the target value to `aa`, and verified its own release. Old close still reported UNKNOWN and did not authorize replay.

This is one successful direct-helper trial with an injected sync delay and decision pause. It does not show that the normal cancellation path invokes the helper, that the old action completed, that all delayed events are impossible, or that physical desktop / MAP01 recovery works. A single sample does not establish reliability or a latency guarantee. The trial shows that the earlier fixture-import failure was avoidable in this harness and that the existing helper can release the held input under these particular isolated conditions; it does not prove the same cause for every prior timeout. The private container exited and the WSLc list was empty afterward.
