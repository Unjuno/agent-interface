# Normal cancellation with held input and delayed XTEST request

One fresh private WSLc/Xvfb allocation used the same local r132 runtime source and pinned image as r141, with a lightweight trial entry point. The synthetic target, source manifest, conditions, command and raw outputs are retained here. The guarded action held `a`, then a test fixture queued an 8-second delayed `b` and blocked the old owner's X sync. The trial called the unmodified `cancel_guarded` directly: there was no forced decision pause, external retirement, cleanup stub or direct private-helper call. This differs from the prior adversarial race; those trials are not a randomized comparison.

The cancel reply reported `cancel_requested`, retired the old process, found its PID-qualified X client disconnected, read the child's shared `a` obligation, and obtained a `readback_verified` release. An independent X client observed `a` and `b` up after cancellation and at the check 8.5 seconds after delayed-request flush; the target's recorded events contain no `b`. The cancel call took 419.55 ms in this one run (disconnect worker 55.63 ms, release worker 354.22 ms). A fresh owner then typed a second `a` into the same target and released it; target value was `aa` and the final keymap was neutral. The old action returned EOF and its cleanup status remained UNKNOWN, with replay disallowed and late-server-request possibility retained. The successful release receipt must not be promoted into old task success or a queue-drained guarantee.

This is one successful normal-path observation on an exclusive private display with injected blocking and delay. It does not resolve the separate race where another caller retired the owner first; the direct-helper r141 success is not an authorized automatic cleanup protocol for that race. It does not demonstrate physical desktop, MAP01, repeatability, or a general latency bound. Source is local candidate code, not merged. The private container exited and WSLc list was empty afterward.
