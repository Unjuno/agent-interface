# WSLc Calc: MCP pending result and delayed save effect

Three fresh WSLc allocations used private Calc/Xvfb, a known blank FODS, main-equivalent runtime f63ead9cec513c50f507be23ca3bc89268c8b49f, pinned image, one CPU, 1 GiB, no network and a 45-second outer timeout. After guarded entry of 731 and 864 with verified release and a reviewed fixed-layout pixel cue, the test used a real stdio MCP client/server in `guarded-x11` mode for observe, mint and one Ctrl+S input. It verified the delivered image digest and polled only the returned call ID; no replay was sent. No model call was made.

- A01 failed before launching the app or sending input due to an unused stale module import; retained. A02 was prepared but never allocated or run. A03/A04 removed the unused import and are fresh allocations.
- A03 running-Calc control: `wait_for_result_ms=0` returned pending with unknown effect and no release confirmation; lookup of that same call ID later returned completed input with verified release, `task_success: null` and replay disallowed. The file snapshot at terminal lookup already contained exactly A1=731, A2=864.
- A04 stopped-Calc case: the owned Calc PID/process group was checked, SIGSTOPed and confirmed stopped before the same single MCP input. It likewise returned pending then completed input with verified release and `task_success: null`; the file at terminal lookup still matched the blank baseline. After SIGCONT, without another input, the file changed and an independently written XML audit found exactly A1=731, A2=864. MCP session close verified release and the observed Ctrl/S keys and mouse buttons were neutral.

The 0 ms response wait is **not** an input deadline or cancellation: the original worker continues and the same retained call is retrieved. The test shows that completed input and verified release do not themselves establish saved task effect. The aggregate audit checks the actual stdio-delivered image hash, observe/mint association, pending and same-ID terminal receipts, exactly one MCP input program, releases, stop/resume timing and independent file contents. Frozen inputs and 305 runtime hashes matched; all run containers were absent and ZIP integrity passed. One observation per arm does not establish MCP deadline cancellation behavior, crash durability, generic queue drainage, arbitrary app behavior, model efficiency or MAP01 completion.
