# WSLc private Xvfb: cleanup deadline during stopped server

Two fresh WSLc allocations used main-equivalent runtime 5c0878064abe1f0bb13fdd2fb5b68938a58bdc36, a private synthetic Xvfb, pinned image, one CPU, 1 GiB, no network and a 30-second outer timeout. In each, the #9864 research worker grabbed the server, pressed button 1 and stalled; its prestarted supervisor retired it at an 800 ms deadline. The input was observed down after owner retirement. A separately prestarted existing `x11_cancel_worker` then received a 400 ms cleanup deadline. No real desktop, Calc target or model was used.

- A01 responsive-server control: cleanup completed its release readback in 53.972 ms; the button was up and target events were press then release. The worker's overall cleanup status remained UNKNOWN and release_confirmed false.
- A02 stopped-server case: the harness sent SIGSTOP to its private Xvfb before cleanup and SIGCONT after the supervisor returned. Cleanup returned UNKNOWN / transaction_deadline and its worker was retired after 403.231 ms. After the server resumed, the observer still saw the button down and only the original press, through a bounded observation beyond the original worker's scheduled late-action time. The harness then explicitly sent a fallback release and verified the button up. The fallback is isolated test cleanup, not the cancelled cleanup worker.

An aggregate audit checks owner/cleanup retirement, timing, input readbacks, target events, absence of the scripted late artifact and fallback. Frozen trial inputs and 305 runtime hashes matched; both containers were absent and ZIP integrity passed. These are single controlled observations. They do not prove no queued operation can ever arrive, behavior when the server cannot be resumed, general process/custody identity, arbitrary input states, real-app correctness or MAP01 completion. The nonzero remaining input during the stalled case is not a successful release; UNKNOWN is preserved.
