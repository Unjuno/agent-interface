# WSLc guarded X11 short-grab boundary probe

This synthetic private-Xvfb probe composes the existing `GuardedSessionOwner` keyboard path with a **research-only wrapper** around its backend `key_state`. For a key down, the wrapper grabs the X server on the same X connection used by the guarded capture and XTEST, invokes the original key-state method (including its native and additional image checks), synchronizes the press, and ungrabs before the scripted 100 ms hold and release. It does not modify the runtime. A separate connection owns an 8x8 overlay window. In the queued case that connection flushes a map request inside the final check while the server is grabbed; it does not wait for the other connection to complete. An XDamage reader on the guard connection is drained by the callback. No model or real game is involved.

| Run | Condition | Result | Grab duration |
|---|---|---|---:|
| s01 | no overlay | guarded press/release completed; target saw both | 21.805 ms |
| s02 | overlay map request queued during grab | guarded press/release completed; target saw both | 14.134 ms |
| s03 | overlay visible before dispatch | native guard refused; target saw no key events | no key-down grab |

For s02 the queued request was flushed after the grab and before the synchronized key-down. A same-connection image captured inside the grab matched the source patch; an independent client screenshot after ungrab and action showed the magenta overlay. The guarded callback's `before_key_press` check and key-down synchronization occurred inside the grab. The action's wait began after ungrab; the attack key was deliberately held beyond the grab. Both completed actions recorded neutral releases and target press/release events; the refused run's owner close also reported neutral release. Every F keymap readback was up. The s02 event reader recorded no damage notification after action; the visible overlay is direct evidence of eventual appearance, not proof of lossless DAMAGE delivery or its exact processing instant.

These are one fixed-order case each, not a latency distribution or hard deadline. The observed durations include the existing guard and artifact work, and cannot be compared directly with the earlier standalone 1–2 ms crop-only probe. Grabbing the entire X server can stall other clients; a blocked call, crash while input is held, delayed queued requests, capture failure, event loss, non-X state and changes immediately after ungrab require separate custody and recovery. The queued window can become visible while the key remains held; a synchronized key-down does not prove that application processing or the entire action saw the old scene. The method does not establish semantic target identity, general atomicity, speedup, MAP01 completion, or readiness for product integration. No cleanup supervisor or forced-crash test is included.

All cases were frozen together and ran once using a 20 s in-container watchdog, WSLc network none, one CPU, 1 GiB, private Xvfb and the pinned image `sha256:6150a4f3c779a51b3ac6a7d93bc1d0450803325efb7ab38ade8b1aaf79c33e25`. The read-only Python runtime subset matched the earlier fixed-patch probe; intervening main changes were research only. The specifically named containers were confirmed exited and removed. ZIPs preserve frozen conditions, runner, images, observation and action receipts, event records and logs. `python audit.py` (Pillow required, normal Python mode) verifies source/image hashes, grab/queue/check/press/wait ordering, preexisting-change refusal, target events and release. The next integration question is a bounded, independently supervised grab/press/release design with failure and queued-input evidence, not a direct promotion of this wrapper.
