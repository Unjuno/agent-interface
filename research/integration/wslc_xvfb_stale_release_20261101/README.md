# Stale X11 release across private display replacement

This follows the [display-supervisor spike](../wslc_xvfb_supervisor_spike_20261101/README.md) with a deliberate stale-release challenge. A fixture held `a` on a private Xvfb, which was stopped and then either retired via its retained pidfd and replaced on a different display, or resumed as a shared-display control. After the old `a` was dealt with (the control required a fixture release), a separate fresh X client held `b`. The old client then attempted to release `b`; an independent query checked whether the new hold survived. Finally a fresh spawned guarded owner typed `a` into a separate target.

| Observation | Retire and replace | Resume same display |
| --- | --- | --- |
| Fresh `b` before old release | down | down |
| Old client release | failed with `ConnectionClosedError` | sent |
| Fresh `b` afterward | still down | up |
| Later guarded task | target recorded `a`; release verified; input neutral | same |

In the replacement arm a fixture released `b` after verifying the hold remained. In the shared-display arm the old release itself cleared the fresh client's `b`. The target event log records those releases; it also records the control's earlier fixture release of old `a`. Both target-scored tasks completed, but neither result is evidence that the old operation's physical release was confirmed. Destroying the old server caused its target to exit with code 1 and discarded its application context.

The held keys and stale release were deliberately generated by test clients, not by an actual stalled guarded owner or a previously queued server request. The new server used a different display number. The test does not establish same-number authentication isolation, automatic integration with cancellation, ownership of a user's display, late-request fencing for arbitrary backends, hard deadlines, MAP01 completion or general reliability. This is one fixed-order pair on a single host.
