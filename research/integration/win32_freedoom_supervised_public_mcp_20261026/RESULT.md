# Win32 Freedoom MAP01 — standard supervised public caller R07–R13

Seven separately preregistered native Windows attempts exercised the current-main `supervised-win32` MCP stdio surface against fresh Freedoom MAP01 processes. The user's authorization covered this PC. No WSLc allocation, Docker, model, or provider was used. Each target-generation hash returned by public `interface_observe` matched the pretrial generation and was copied unchanged into the one public dispatch. These trials are not pooled as a reliability estimate.

| Attempt | Result | Disposition |
|---|---|---|

| R08 | Public observation and generation binding succeeded. The client saw `pending`; after it exited, the persisted action report resolved to completed with a verified release receipt and separate neutral readback. | Normal release/readback supported. Task oracle was not called; public task success remains null. A separate later capture showed 90.34% world-pixel change but is not an oracle certificate. |

The independent oracle waits one second after action completion or recovery, captures the same target through a fresh `Win32Backend`, and scores RGB changes in `x=0..639, y=0..399` against the pre-dispatch baseline. A verified successful task means only “visible forward response above the preregistered 5% pixel-change threshold”; it does not mean the level was completed. R11 and R12 are separate single samples and do not establish reliability. R13 confirms recovery and task failure as distinct outcomes.

## Scope and remaining work

R12 advances live standard-caller generation binding, normal release/readback custody, and an independently checked task effect. A post-R12 code-path investigation found why R09's two status rows diverged: the standard dispatch worker can return while cancellation is still pending, then a later `interface_results` refresh updates only the cancellation row after owner recovery completes. The standard action row consequently remains `running`, preventing the independent task oracle from running. PR #9574 makes a later refresh promote a standard-program action to `recovered` only when cancellation, action, and owner receipts match operation and target generation and the owner confirms recovered release; terminal unconfirmed custody stays `unknown`. A delayed-recovery integration test covers the same public result/oracle path. R13 then exercised the late-recovery path live on merged main: the first result read returned the action as `recovered`, the exact generation-bound oracle ran once, and its failure remained separate from release confirmation. R09's immutable packet is unchanged.

These attempts do not establish a physical release deadline, release under blocked platform I/O, recovery bounds for a blocked native producer, continuous-time stop behavior, matched efficiency, model/provider economics, or broader reliability. Continue by measuring producer-startup delay and then run a preregistered blocked-I/O recovery experiment under an authorized resource boundary.

Private raw packets `win32_freedoom_supervised_public_mcp_20261026_r07` through `..._r13` retain preregistrations, public MCP requests/replies, producer/session receipts, PNG/BGRA captures, cleanup records, and SHA-256 manifests. The manifests for 8, 28, 110, 36, 37, 36, and 33 files respectively were checked with zero mismatches. R11's evidence-reference mismatch is detailed in its packet's `EVIDENCE_REFERENCE_RECONCILIATION.md`; R12 and R13 receipts point to their own hash-matching raw results.
