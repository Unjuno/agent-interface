# Real Calc: blank guard stops its own multi-key entry

This preregistered single WSLc run connected the opt-in OCR graph from PR 9994 to an actual LibreOffice Calc window in private Xvfb. The blank file was independently checked before input, A1 was already selected, and a reviewed fixed pixel region supplied independent blank evidence. Two expected values were 641/283. The test used no model; the OCR callback invoked actual bounded Tesseract on current crops when the region no longer matched the blank baseline.

The graph admitted entry and the actual input backend recorded four key emissions. On the next key press, the cell region no longer matched the blank baseline; the fresh guard saw `cells_blank=false` and refused the remaining action. The method returned `SAFE_YIELD` / `execution_failed`, zero completed transitions and no pending effect; the failed-operation receipt explicitly says partial input may have occurred. Both the action release and owner close recorded neutral input. The saved FODS remained byte-identical to the original blank file. The unsaved in-memory document may contain partial edits; the blank saved file is not proof that no input occurred.

This is a **negative integration result**: a guard that correctly rejects an external change before dispatch can also reject the action's own expected partial edits when rechecked between key presses. The current opt-in graph cannot be claimed to complete this multi-key Calc entry from this run. A repair needs a bounded, capture-bound way to distinguish authorized partial progress from external changes while retaining input release, finite failure and independent saved-effect checks; simply disabling the guard would lose the stale-input protection. No repair or replay was attempted here.
