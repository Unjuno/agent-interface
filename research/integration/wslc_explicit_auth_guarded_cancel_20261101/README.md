# Child-scoped authority in a guarded cancellation composition

This new WSLc pair combines the [explicit child authority draft](../wslc_owned_child_xauthority_20261101/README.md) with the earlier [guarded cancellation/display replacement fixture](../wslc_guarded_owner_display_cancel_20261101/README.md). While each old and fresh owned guarded process was started, the harness parent held a deliberately invalid `XAUTHORITY`; the owner and its prestarted cleanup supervisor received their private display authority explicitly. The harness temporarily changed its own environment only to open its independent Xlib connections, and restored the invalid sentinel before starting each guarded owner. Target subprocesses received explicit environments.

In both arms the actual old guarded owner sent `a`; the separate target recorded it and an X client observed the key down. A test hook paused that owner after the press was synchronized. The harness stopped the private server and invoked actual guarded cancellation. Both cancellation results retained `cleanup_status=UNKNOWN`, no release confirmation, no replay, an `a` obligation and a retired owner; the old guarded call ended with `EOFError`. The bridge cancellation-signal `input_dispatched=false` is scoped to that signal, not the already-observed action; see [#10089](https://github.com/Unjuno/agent-interface/pull/10089).

In the retirement arm the harness explicitly retired the old owned display and started another; an injected stale `b` release on the old connection failed and a fresh client's `b` remained held until fixture release. In the resumed-server control the stale release cleared the fresh `b` hold. Each arm then completed a fresh guarded `a` task, independently recorded by a target with a verified release and neutral final X state. The old target exited 1 when its server was destroyed; its application context was lost. The resumed old target's final value was `aaa` after an initial `a`, consistent with the separately investigated autorepeat possibility but not a successful old-task result.

Both fixed-order allocations used main `e5925b6bd99fd4ff3f8e0bda5ed4d7cc02d92c4d`; `owned_guarded_session.py`, `cancel_supervisor.py` and `private_display_owner.py` match draft [#10088](https://github.com/Unjuno/agent-interface/pull/10088) `926ba07214b5ab53ff38f66af5c0947606850118`. Other source comes from the earlier [#10074](https://github.com/Unjuno/agent-interface/pull/10074) snapshot, so this is a retained mixed tree, not an integrated commit. The image was `sha256:6150a4f3c779a51b3ac6a7d93bc1d0450803325efb7ab38ade8b1aaf79c33e25`, one CPU, 1 GiB memory limit, no network and no pull; WSLc reported swap was not limited.

Both launchers returned zero on the frozen fixture criteria. [raw.zip](raw.zip), SHA-256 `309c3ad2a0e200464e96e3ad3755546a700d4422c9833b315b7d9344328ad15d`, retains source, conditions, logs and receipts; ephemeral authority files are excluded. The audit checks source hashes, parent sentinel at the owner starts, actual old target press, cancellation custody, event order, key states, fresh task and process exits. The earlier separate connectivity test established the supervisor could use the explicit authority; this stopped-server pair did not establish that its cleanup connected or released input.

The owner pause and stale release were injected; display retirement was orchestrated by the harness, not automatically wired into cancellation. Old physical release, old-task success, real queued-request fencing, same-user isolation, hard deadlines, MAP01 completion and general reliability remain unproven. This pair does not justify terminating a shared or user display.
