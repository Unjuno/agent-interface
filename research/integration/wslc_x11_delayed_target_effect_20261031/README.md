# WSLc private Xvfb: target-side effect after owner deadline

Two fresh WSLc allocations used main-equivalent runtime 276183bbc8d7929ef5140e015938536f07587528, private synthetic Xvfb and a synthetic event-handling target, pinned image, one CPU, 1 GiB, no network and a 30-second outer timeout. A research-specific supervised worker recorded custody, grabbed the server, checked its target, issued one XTEST button press/release and synchronized the X connection before a 600 ms deadline, then intentionally stalled. An existing prestarted supervisor retired it at the deadline with UNKNOWN / transaction_deadline. The worker's additional scripted pair was scheduled two seconds later; the harness observed beyond that time and no late artifact was produced. This is not public guarded dispatch or a real app.

- A01 running-target control: the synthetic target handled both events and recorded its effect before the deadline; the supervisor later returned UNKNOWN because the worker stalled. The target was already affected when that result returned.
- A02 stopped-target case: the harness SIGSTOPed the target before the pair and confirmed process state T. The server synchronized the original pair before the deadline; no target effect file existed when the supervisor returned UNKNOWN and reported the worker retired. After the harness SIGCONTed the target, it handled the original press/release and recorded its effect **after** the supervisor return. The observed effect was caused by the earlier submitted pair, not a replay or a new post-retirement input request. Final button state was neutral.

The aggregate audit checks process and window IDs, event types, server-sync, deadline, supervisor-return and target-handling timestamps, the controlled target stop/resume, and observation past the worker's scheduled extra pair. All frozen inputs and 305 runtime hashes matched; both containers were absent and ZIP integrity passed. This is a single controlled schedule per arm. It demonstrates why process retirement, neutral input and no new emissions cannot by themselves certify that the target has drained already-delivered events. It does not prove event delivery for all X servers, real applications, other platforms or crash conditions, nor provide a production drain/reconciliation protocol. UNKNOWN remains necessary until task effect is reconciled.
