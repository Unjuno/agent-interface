# R562: child spawned after parent death

One preregistered no-GUI/no-input synthetic WSL Ubuntu Python 3.12.3 trial. The run directory was created exclusively and events carry a unique run ID. The supervisor was gated before its unconditional spawn; the controller killed and reaped the parent before releasing the gate. The structured timestamps show child spawn after parent reap, followed by supervisor detection of pipe EOF and the child-reaped receipt. The child's pidfd was non-readable before the EOF check and readable afterward; the supervisor pidfd also became readable. No fixture emergency kill was recorded. Exit 0 means the **counterexample was observed**, not that the scheme is safe. Exact conditions, script, output and events are in raw.zip; pre-run script SHA-256 `44138a79abc6fcf238ade90592751e2b724fbfb61b6b4f3c16b589f1a90d9bca`.

The child was a sleeping fake and did not perform owner initialization or input. This establishes only that this deliberately unconditional supervisor can create a child after parent death. PID files are still read before pidfd acquisition, without an independent identity-binding proof, and supervisor exit status was not collected independently. A pre-spawn liveness check alone has its own check/spawn race; an unpermitted child must remain unable to execute effects until authority is safely established. No production, WSLc, input-release, MAP01, timing-bound or reliability claim follows.
