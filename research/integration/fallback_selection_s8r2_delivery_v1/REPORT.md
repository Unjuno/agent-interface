## Result

Every arm has 12 independently initialized app/server cases. The task is the exact
whole value `7` in the intended widget and the unchanged protected field `keep-42`.
The two widget classes are classic Tk Entry and Text, not two independent toolkits
or production application domains.

| Native replacement recipe | Cases | Exact whole value | Wrong whole value in editable cases | Disabled cases | Pre-input refusals | Native key events |
|---|---:|---:|---:|---:|---:|---:|
| CTRL_A then text | 12 | 2 | 8 | 2 no-effects after input | 0 | 72 |
| Home / Shift+End then text | 12 | 8 | 2 | 2 no-effects after input | 0 | 96 |
| Selection-confirmed, at most one document-extent refinement | 12 | 10 | 0 | 2 no-input refusals | 2 | 100 |

The verified arm succeeded in all 10 editable cases, refused both disabled cases,
and used exactly two one-shot refinements, both on multi-line Text. It did not
claim those two refusals as completion. Every protected field remained unchanged.
These finite directed counts are not population reliability or failure rates.

A concrete formal example begins with `north\nsouth` in Text:
- CTRL_A produced `north\n7south`.
- Home / Shift+End produced `north\n7`.
- Selection-confirmed refinement produced exactly `7`.
The first selection covered only offsets [6,11), not the whole [0,11) document.
The candidate observed that actual selection, expanded once using Control+Home /
Control+Shift+End, checked again, and only then sent the replacement digit.

The empty Entry positives matter: all three recipes succeed there, so an empty
fixture alone would have concealed the obligation mismatch. The disabled controls
also matter: backend input completion is not evidence of application modification.

## Method and independent evidence boundary

The actor uses standard Entry/Text class bindings. Its appended audit bindtag logs
actual KeyPress/KeyRelease processing. IPC after startup can only query a snapshot
or terminate; it cannot insert/delete task text. A release-count barrier waits for
real app processing, rather than treating XSync as task completion. These authored
barriers are explicitly fixture-specific, not a generic GUI service.

Candidate stdin contains only scope, target, generation, source/current sequence,
actual content/selection/caret, editability, focus and key-release count plus the
bounded phase/refinement counter. It has no scenario name, file path, expected
outcome, native oracle, future effect, protected-field result or DISPLAY. The app
config contains setup labels but app code does not branch on policy or expected
outcome. Initial text itself is legitimate current evidence, not a hidden label.

The auditor imports neither candidate, runner, backend, Tk nor Xlib. It reads
original raw wires, native app key journals, readonly snapshots, app-written final
values, raw capture bytes and process receipts. It reconstructs the ordinary edit
from actual pre-key selection/caret, checks the prospectively frozen result matrix,
and separately verifies protected content and all event identities/counts. Capture
integrity is checked; no OCR/semantic interpretation of pixels is claimed.
Independence means a separately implemented executable/process by the same author,
not external human review or independent authenticity of the cooperative app.

The unit controls cover wrong scope/generation/focus, source ordering, changed
content, noneditable state, bad/Boolean indices, unknown fields, opaque renaming,
input immutability and exhausted refinement. These are not added live trials.
Raw controls change final effect, native event history, partial selection claims,
scope, authority, protected state, exits, event count, refinement, pixels, Boolean
generation and independently retained final value. All started from an audit-passing
original; every mutation changed data and produced a semantic/integrity refusal.
