# Private display draft: bounded lock waits

The prior draft serialized cleanup but could wait indefinitely for its cleanup or state lock. A controlled test held each lock while another thread invoked close or retire; both retire cases exceeded the test's wait, while close had no timeout argument. Invalid `NaN` and infinity startup budgets also reached side effects instead of being rejected before startup. The pre-fix console output is not included in this archive.

Close and retire now share one monotonic timeout budget across acquisition of both locks and the child wait. If either lock cannot be acquired or the budget is exhausted before retirement, they return `unknown`; they do not claim a completed retirement. Startup, close and retire reject nonpositive, boolean and nonfinite timeout values. The controlled lock test verifies that `unknown` is returned and the server remains alive when either lock is held, then cleans up after releasing the test lock.

Eleven tests passed in each of two fresh WSLc containers, normal Python and `-O`, using pinned image `sha256:6150a4f3c779a51b3ac6a7d93bc1d0450803325efb7ab38ade8b1aaf79c33e25`, one CPU, 1 GiB memory limit, no network and no pull. WSLc reported swap was not limited. [raw.zip](raw.zip), SHA-256 `9624db8549928c3297d9000073fe68c2d6d1c98b2eceaa3821acffe22f2fa27a`, contains source, tests, hashes and both post-fix outputs.

These tests bound lock acquisition and the requested child wait in controlled cases, not the entire operation: scheduling, process creation, signals, descriptor close and other operating-system calls have no demonstrated hard bound. A caller must retry or otherwise resolve `unknown`/`pending` without assuming retirement. Other concurrency and process failures, cookie lifecycle, resource exhaustion, broader suites and cancellation/MCP integration remain unverified. Earlier held-key composition used an earlier revision; no physical release, finite task recovery or MAP01 completion is established.
