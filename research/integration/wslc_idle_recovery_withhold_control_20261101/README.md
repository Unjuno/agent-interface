# Withheld-input control after an idle capture timeout

This is one new WSLc control following the [a07 fresh-session synthetic task](../wslc_idle_recovery_preflight_race_20261101). It uses the same frozen runtime prototype and separate X target, on a new private Xvfb with one CPU, 1 GiB and no container network. The prototype remains **unmerged**.

As in a07, the test observed the private server stopped and the read-only capture worker pending before a 500 ms deadline. The observation returned unavailable while the server remained stopped; after resume the retired worker exited and the old owner still had sequence 1 and required review. A fresh owner captured and minted the textured target, but the test deliberately withheld keyboard input. During a 2,005.794 ms window the target process remained alive and wrote no key-event file; final X input was neutral and the target and server exited zero.

In the earlier a07 cell, the fresh guarded `a` action completed, release was verified, and the same target source recorded an `a` press/release and value `a`. This withheld cell makes a spontaneously recorded key event less plausible in the particular tested window. It is a single sequential, fixed-order pair on separate X servers; the target's lack of an event file is not independent proof that no event could have been missed. The old operation was read-only and no key was held across the stop. This is not a held-input recovery, MAP01, model-driven, general reliability, or hard real-time claim.

It audits retained records rather than independently observing historical events. WSLc reported its memory limit excludes swap.
