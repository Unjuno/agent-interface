# 親プロセス終了と relay 終了待ちの境界

Windows / Node 24.19.0 の実プロセスで、**親の終了コード 0 と、ホストの `close()` 完了は別である**ことを確認した。元の relay ソースは変更していない。

| 条件 | 観測 |
|---|---|
| 通常の直接子プロセス | 親が終了し、元の `close()` と `exit.json` が成立 |
| 通常設定の子孫が stdout を継承 | 親終了直後に子孫も終了。保持条件が成立せず HOLD。終了記録読み取りで最初の調査 driver が停止 |
| 独立設定の子孫が stdout を保持 | 親の実終了後 104.4059 ms の観測でも `close()` が未完了、`exit.json` なし。子孫を解放すると元の待ちが完了 |
| 独立設定の子孫が stderr を保持 | 親の実終了後 108.5035 ms の観測でも同じ未完了。子孫を解放すると元の待ちが完了 |

各条件は一回の通常の構築観測であり、性能の統計ではない。100 ms は比較用に設定した呼び出し側の観測間隔で、production の終了期限を意味しない。待つ時間だけを区切っても、保持している子孫やパイプの解放にはならなかった。

実行前に Windows の親・子孫プロセスハンドルを取得し、PID と生成時刻を結び付けた。保持条件の観測点では親は実際に終了、子孫は実際に稼働中だった。解放後は、取得した全 7 ハンドルで終了コード 0 を確認し、ハンドルと記録用スレッドを閉じた。元の終了待ちや要求は再送していない。product の要求送信は 0 件。

最初の driver の終了コード 1、保持条件不成立、未実行の最初の stderr 条件、終了記録欠落は保存した。通常設定の試験を繰り返すことはせず、`detached: true` による独立設定を新しい二条件として事前固定した。Node の [バージョン固定 libuv ソース](https://github.com/nodejs/node/blob/v24.19.0/deps/uv/src/win/process.c#L1016) は、通常設定の子を親終了時に停止する Job に割り当て、独立設定ではその割当を省く。最初の終了はこの実装と整合するが、実際の Job の識別は測っていない。

保存データを別実装で照合し、raw とイベント、Windows の終了状態、生成時刻、解放順序、同じ終了待ち、終了記録を再構成した。タイムラインと型などを壊した 9 個のコピーをすべて拒否した。元の実プロセス試験は再実行していない。

対象 main は `ba1c4d966bc098e8f9f7e9e6df85f1281daa1582`、元の `relay_client.mjs` は 12829 bytes / SHA-256 `0a935142a8878fb90f212e004a9e8ffe47224d1505c6cee670960db03c38312b`。初回の [事前記録](https://github.com/Unjuno/agent-interface/issues/57#issuecomment-5968931537) と、新条件の [事前固定・最初の結果](https://github.com/Unjuno/agent-interface/issues/57#issuecomment-5968975337) を既存の親 Issue に置いた。

現在の API は任意の子孫の強制終了、全体の硬い終了期限、GUI の cleanup を約束していない。この観測はその契約への違反を意味しない。統合側で有限の回復を証明するには、親終了だけで完了扱いせず、残る子孫・パイプの所有と解放、または未完了の明示を扱う必要がある。実 backend、物理入力解放、タスク効果、モデル呼び出し削減、総資源改善は未測定。runtime の修理、main 反映、コンピュータコントロール全体の完成は未実施。
