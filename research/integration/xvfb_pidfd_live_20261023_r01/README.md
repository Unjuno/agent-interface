# Local Linux pidfd process-only trial — R01 first outcome

**Disposition: FAIL before the three declared signal schedules.** The one
invocation exited 1. It was not rerun. No GUI/XTEST/SendInput operation or task
effect was attempted. No WSLc allocation, image/container RPC, or Docker
operation was used. This is a local Ubuntu WSL2 process-control attempt.

The target helper fix is merged in PR #9420. Probe code was frozen at
`8eac9f9e5ff05cc0f2739a8688f96cbd99f67b92`, and conditions were committed at
`d908ce58f` before execution. The helper source and executable AST hash are
retained with the result. Only that exact standard-library helper function
was compiled from its AST; the integration module and X libraries were not
imported. Signal calls were forwarded to real Linux pidfds; path/timer faults
were predeclared, but their schedules were never entered.

## What actually happened

The capability preflight found Python 3.12.3, pidfd APIs, `/usr/bin/Xvfb`, and
no `:88` lock/socket. The probe launched its own Xvfb child (PID 386), opened a
cleanup pidfd and wrote its exact process/stat/fdinfo receipt. The server did
not create the expected `/tmp/.X11-unix/X88` pathname within the declared
five-second readiness wait. `result.json` contains an empty `cases` array.

`xvfb.log` records a `/tmp/.X11-unix` mode warning and failure to create a Unix
listener, followed by nonfatal XKB warnings. A read-only follow-up found the
directory is not a symlink and its mode is `0777`, rather than the `1777`
mentioned in that log. The directory was not modified. This does not prove
that every X transport was unavailable: no X connection was attempted, and
earlier retained trials also had a pathname-listener caveat.

The finalizer sent CONT and TERM only through the exact owned cleanup pidfd,
reaped the child with exit code 0, and recorded confirmed exit. A separate
post-run process/filesystem query found that PID, the `:88` lock, and the
socket absent. Cleanup succeeded; that does not turn the failed trial into a
passing STOP/CONT experiment. The healthy/fault schedules remain unexecuted.

## Next action and limits

Before a new, separately frozen process-only attempt, revise readiness to
observe the owned process's actual state rather than requiring an X transport
pathname that the signal-only question does not need. A GUI trial still needs
its own real connection/readiness evidence and an owned input domain. Do not
chmod a shared socket directory or reuse this consumed attempt.

No actual helper STOP/CONT result, physical release, native target fencing,
application task/MAP01 effect, latency bound, efficiency or reliability has been
established here. The verified-unused WSLc environment question remains pending.
