# Windows app-server descendant pipe-retention result

## H / T / D / C / U

**H.** The current `CodexAppServerClient.close()` terminates and reaps only its direct `Popen` child. If that child starts a descendant inheriting stdout, the descendant may keep the client's reader blocked beyond `close()`'s timeout.

**T.** One isolated Windows/Python 3.12.10 construction run imported the exact current-main `research/live_control/codex_app_server_client_v2.py` source (SHA-256 `243d3c0b242a34317b5cc6234df2f323322271e670c7f38a3b25a35e0b13c768`; main source snapshot `4d42238694c55aaa29bf47cb13a5b8d4c5d4074a` (the evidence branch is based on `853a867fb554c04d8f1223f9525f9eaf7d2792b6`; the pinned source blob is unchanged)). It started a real client child and a 30-second grandchild inheriting its stdout/stderr, then called `client.close()` with the default 5-second bound. Descendant liveness used Win32 `OpenProcess` + `GetExitCodeProcess`, avoiding a signal operation. The direct client child was reaped, while the descendant remained active, `close()` raised `TimeoutError: app-server reader close timed out`, the reader thread remained alive and stdout remained open. Cleanup targeted only the recorded test descendant PID/tree; afterward the reader ended and the descendant was absent.

**D.** `FAIL_BOUNDED_CLIENT_CLOSE_WITH_INHERITED_DESCENDANT` on this Windows host, while retaining the fact that the client reports its failure instead of claiming successful retirement.

**C.** `windows-v2-result.json` and exact source/test scripts are retained in this directory. `audit-v2.json` is generated by the saved auditor and checks source identity, pre/post states, expected error, cleanup, and process absence. `audit-v2.py` itself uses Win32 process query APIs only.

**U.** This proves the client/pipe ownership boundary with a synthetic child process on this host. It does not prove ordinary Codex app-server sessions spawn descendants, test a process-tree shutdown policy, or cover macOS/Linux lifecycle semantics. ## Measurement correction

The first Windows draft and its separate Popen control are preserved as `result.json` and `control-result.json`, but their descendant-liveness fields are **invalid and must not be interpreted**. Those scripts called `os.kill(pid, 0)` as though it were a non-destructive liveness query. On Windows, Python documents that any `os.kill` signal other than `CTRL_C_EVENT` / `CTRL_BREAK_EVENT` calls `TerminateProcess` ([Python `os.kill` documentation](https://docs.python.org/3/library/os.html#os.kill)); therefore the check itself could terminate the test descendant. The corrected run uses Win32 process-query APIs and does not use `os.kill(pid, 0)`. The earlier raw outputs have not been overwritten. A second default-timeout attempt initially raised the same reader timeout before its first script persisted a result; that attempt is superseded by the exception-safe corrected run and is not counted as evidence.

## Reproduction


The reproduction writes its raw JSON before returning. It intentionally terminates only the exact descendant PID/tree it created after capturing the timeout state.


## Integration follow-up: process containment at client startup

A Windows-only experimental `process_factory` prototype was then connected to the exact same `CodexAppServerClient`. It creates a private Job Object with `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`, starts the Popen child with `CREATE_SUSPENDED`, assigns it to the job before the primary thread resumes, and wraps Popen so closing the job after direct-child wait terminates inherited descendants. The primary thread is located while the child is suspended and resumed only after successful assignment.

The first integration harness run (`integrated-job-result-a01.json`) returned from client close, ended the reader and removed the descendant, but its final cleanup field recorded an attribute typo (`client.close_job` rather than `client.process.close_job`). The raw first outcome is preserved. A02 corrected only that harness accessor and repeated the bounded integration probe. The actual client `close()` returned normally; the Win32 state query found the descendant active before close and absent after it; the reader had ended at return. `audit-integrated-v2.py` independently checks both baseline failure and A02, candidate source hash, the exact assignment-call-before-resume order, retained A01 harness error and process absence. `integrated-audit-a02.json` returns PASS. The initial audit and result are retained as `integrated-audit-a01.json`; A02 strengthens the ordering check so the declaration site cannot satisfy it accidentally.

This is feasibility evidence for an adapter on this Windows host, not an adopted client fix. The prototype uses Popen's private `_handle` and requires exactly one suspended initial thread. Nested job constraints, breakaway descendants, broader startup failures, interpreter/process-factory compatibility, macOS/Linux behavior, and physical app-server sessions remain untested. The existing `CodexAppServerClient.close()` also does not close its parent-side stdin/stdout/stderr stream objects; the harness explicitly closes them after measuring reader completion. Therefore the experiment resolves the demonstrated descendant-held reader boundary only within its tested composition, not all process/client resource-retirement requirements.

Relevant platform contracts: [AssignProcessToJobObject](https://learn.microsoft.com/en-us/windows/win32/api/jobapi2/nf-jobapi2-assignprocesstojobobject), [suspended thread startup](https://learn.microsoft.com/en-us/windows/win32/procthread/suspending-thread-execution), and [`JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`](https://learn.microsoft.com/en-us/windows/win32/api/winnt/ns-winnt-jobobject_basic_limit_information).
