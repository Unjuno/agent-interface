# Client lifecycle for early interruption

stopped_client_v1.PendingAction tracks one already-submitted action from an explicit received cursor. It never submits input, creates a lease, retries a command or polls automatically. Its states are awaiting_outcome, input_stopped_capture_pending, terminal_received and needs_reconciliation. A read-only poll_request uses the latest consumed cursor and own action id; after input_stopped it waits only for terminal.

Contiguous replies are checked against recorded cursor positions. Exact overlapping replay is accepted, conflicting or unavailable replay requires reconciliation, and history is bounded to 4096 events per action. Timeouts and batch boundaries retain pending state. Foreign action outcomes cannot finish the tracked action. Stop evidence requires recorded admission, verified empty input release and a known focus/surface reason. Terminal after stop must preserve interruption and reason. Missing identity, duplicate admission/outcomes, closed stream before terminal, gaps, transport errors and unattributed rejections require reconciliation. Uncertainty is sticky. Returned events are deep copies.

These are recorded consistency checks, not full nested schema validation or authenticity. terminal_received is not task success, current input permission, or a guaranteed instantaneous idle response: normal runtime admission still decides whether the backend is available. Image references remain historical; this module does not resolve image files or refresh capture authority.

## Validation

results/stopped-client-01 has twelve controls: stop plus terminal in one batch, timeout, exact replay, foreign terminal, missing admission, gap, close before terminal, duplicate stop, cause mismatch, unverified release, future cursor and sticky rejection. It also confirms that a generated pending poll has no command. Replay of the original real-socket probe remains pending across its timeout and enters reconciliation on that probe's deliberately premature submit rejection.

results/stopped-transport-02 attaches PendingAction to a fresh actual private AF_UNIX/child-process run with the frozen synthetic capture gate. Six exchanges and eleven raw events are compared to contiguous reply history. States observed in order are pending after early stop, pending after terminal timeout, pending after matched cancellation response, then terminal_received after explicit capture-gate release. The original focus cause remains, only the in-progress capture completes, no tail input executes, and runtime/bridge exit 0. Early submit round trip was 34.607804ms here; this is synthetic transport timing, not GUI or model latency. The probe asserts the generated poll request shape, while its networking harness explicitly sends the reads.
