# Expired programs return post-release observations without renewing input

executor_v9 extends the existing release-followup path to expired programs, in addition to the unchanged focus/surface interruption cases. After verified release it emits input_stopped with cause expired, collects up to two passive samples using the existing80ms waits, then emits terminal with status still expired. It does not change the original input deadline, continue program steps, renew a lease or infer task completion. Explicit cancellation can suppress/interrupt collection; unverified release suppresses it entirely. New cause_servo_interactive_v6/socket_v8 entries opt into this candidate; previous frozen entries remain unchanged.

A fresh actual Inkscape seed240 run admits a Shift_L hold1500ms followed by text999 under a500ms deadline. The hold expires, the Shift input is released and the text step never starts. Two observations captured after verified release precede the expired terminal; the caller's terminal reply contains the newer image. Latest capture is205.250ms after release and terminal follows at228.801ms. The early input_stopped event precedes this delay. These timings are one real modifier-hold trial, not a latency estimate for arbitrary app capture or model inference.

Audit replays20 events and8 exact transported frame/PNG pairs, verifies source/runtime hashes and continuation slices, exactly one Shift admission before the deadline, keys_held evidence, zero tail-step execution, verified empty held inputs, no input during post-release collection, and passive capture timestamps between release and terminal. Saved SVG remains50/50/40/30. This is expected-expiry observation success, not an editing task success. Driver exits0 and sockets are removed. Evidence is results/expiry-observation-01; audit_expiry_observation_v1.py replays it under Linux without new inputs.

Three fake-backend control cases verify expired status is retained with two captures, failed release yields failed status/no captures, and explicit stop yields no captures. The first control harness raced fast executor completion while reading active[2] and failed; its source and failure artifact are retained in expiry-observation-controls-01. Corrected v2 handles an already-completed job and all three controls pass in expiry-observation-controls-02. This was a test-harness repair; no live runtime rerun was needed. Fake controls do not replace the actual held-input expiry experiment.

Limits: collection is cooperative and cannot preempt a hung backend snapshot/X call. Equality of two frames is not application readiness. Expired remains an interrupted program and may have partial effects; the new observation must be interpreted independently. The update closes the stale-observation gap but does not resolve the first-click freshness versus whole-program-lifetime mismatch identified in READY_REPLAN_INK.md. No blanket deadline extension or promotion of the mixed readiness result is justified.

Decision: use the new expiry-observation entry in subsequent interruption experiments. Next separate fresh target activation from subsequent bounded input duration, while preserving a checked handoff between phases and using the post-release images if either phase expires. Do not equate a saved artifact with a completed program or automatically replay its uncompleted tail. Human-like live control and broad domain coverage remain open.
