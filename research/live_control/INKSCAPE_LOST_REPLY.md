# Actual GUI result recovered after client abandoned the response

The checkpoint-based received_exchange_v2 caller ran against the unchanged private socket and cause-servo/executor8 Inkscape fixture, seed232. A scripted selection was followed by one six-step move-save program: focus X, select text, enter88, Return, Ctrl+S, observe. The request was sent through a real AF_UNIX socket, which the test client deliberately closed immediately after sendall and before any recv. It then raised a marked test exception. This models receiver abandonment, not a naturally occurring network outage.

At connection close, server receipt was unknown; sendall alone was not treated as proof of application execution. The caller's received continuation remained exactly at its pre-send checkpoint. The same bridge process was checked live. A new command-free read from that checkpoint, scoped to move-save, recovered the original command echo, admission, observations and completed terminal. No edit request was resent. The next and only new command was finish after recovery.

Six exchanges returned replies and one request had its response abandoned. The49-event runtime trace has exactly two accepted programs: select and move-save; move-save-once is echoed once and its Ctrl+S step appears once. All terminals verify input release. Nine image frames reconstruct exactly. The assistant subsequently viewed final image009 and saw X88,Y50,W40,H30 with Document saved. Independent parsing of the saved SVG confirms those values and no transform. Bridge/driver exited0 and both private socket paths were removed.

The predeclared plan, lost request hash, explicit zero received-response bytes, unchanged checkpoint, all recovered event slices, unique program/save step, images and saved SVG are checked by audit_inkscape_lost_reply_v1.py. Results: results/inkscape-lost-reply-01. Source files are pinned before launch. This was scripted actual GUI use; there was no extra model call or autonomous visual planning in the driver. No model latency or general speed claim is made.

The test's ConnectionError is deliberately raised after a real connection close. Its recovery policy explicitly chooses observation-only reads; received_exchange_v2 itself does not persist an unresolved-command lock that prohibits a caller from proposing another command. The test also does not cover partial request bytes, a server crash, event-ring eviction, disk loss or resume from a different process. Emergency harness cleanup terminates its bridge on failure and is not a production supervisor. These remain material boundaries.

This verifies actual caller migration and one positive lost-response recovery path.
