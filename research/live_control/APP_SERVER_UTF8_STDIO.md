# Explicit UTF-8 protocol streams

The app-server protocol is JSONL with UTF-8 bytes. The journaled client now passes encoding="utf-8", errors="strict" to its process factory. This is the sole 35-byte client delta over fixed response-ownership head6353a588. Its independent binary stderr reader still uses the buffer directly; diagnostic bytes are not decoded or granted protocol authority.

A fresh Windows/Python3.12.10 native comparison runs its driver with UTF-8 mode explicitly disabled and observes cp932. Fixed7125 accepts a UTF-8 label as mojibake and a standalone invalid0x80 as U+0080. The private explicit-codec candidate preserves the valid label and rejects invalidUTF8 as a client error. Four actual peers each receive one original request and exit0; captured request/response/stderr byte images and peer write-return counts are retained outside the source tree. Earlier peer Unicode experiments/model attempts are not replayed or relabeled.

Two new portable binary-peer regression methods require nonASCII UTF-8 fidelity and invalidUTF8 refusal. The49-method selection also includes ten pending-ownership, nineteen stderr/EOF/journal/reader and eighteen consumer/planner/model controls. Normal and optimized runs each pass49 with UTF-8 mode disabled. The invalid-byte test intentionally retains the existing reader UnicodeDecodeError traceback and closed-channel AppServerError; this change does not implement structured decode-error diagnostics or general malformed-message recovery. Driver/test exit0 is not proof of absence of that expected background exception.

The complete proposed bundle retains stderr draining, active-request ownership, monotonic request IDs and final retirement, the reply-after-issued EOF fixture and explicit pending ownership in the directed held-journal fixture. Runtime catalogue registration preserves every prior byte/order with one new append before the entry point.
