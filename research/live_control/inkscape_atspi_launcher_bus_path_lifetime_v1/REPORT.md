# AT-SPI launcher-generated bus vs Inkscape object-path lifetime

Decision: **REJECT_LAUNCHER_GENERATED_BUS_ALONE_AS_DEFUNCT_CAUSE_SCOPED**.

## Question

After #451 rejected Registry presence alone and #460 rejected listener registration alone, does changing only the accessibility-bus lifecycle/configuration from a manually started direct bus to one generated by the official `at-spi-bus-launcher` reproduce the labelled A/B path defunct/reincarnation seen during #415 construction?

This rung does **not** test application-side session `org.a11y.Bus` discovery. In both arms Inkscape receives an explicit `AT_SPI_BUS_ADDRESS`. The candidate bus is nevertheless the real bus spawned by the official launcher with the official Registry activated on it.

## Frozen design

Publication base `defb76363803ac76875924b7246de76a1f6d6963`, Issue #488. Six fresh first sessions, schedule `direct, launcher, launcher, direct, direct, launcher`; no retry or replacement.

Common: private Xvfb/Openbox, unmodified Inkscape, same labelled SVG, Layers/Objects open -> discover A/B -> close -> probe old paths -> reopen -> rediscover -> probe old paths, final X11 keymap empty. No selection-identity scoring, document edit/save/effect, model or game call.

Baseline uses a manually started private accessibility `dbus-daemon` and official Registry. Candidate runs the official `at-spi-bus-launcher` in a private chroot and uses the launcher's real accessibility bus/Registry. To prevent the app from consuming the chroot-local `/run/at-spi/bus` path through session discovery, the app uses a separate ordinary session bus and is explicitly given the actual host-visible path to the same launched accessibility socket.

## First measured result

| arm | n | old A/B readable while panel closed | reopen path identical | old path resolves original Name | final keymap empty |
|---|---:|---:|---:|---:|---:|
| manual direct bus | 3 | 3/3 | 3/3 | 3/3 | 3/3 |
| official launcher-generated bus | 3 | 3/3 | 3/3 | 3/3 | 3/3 |

All candidate cases had genuine Registry ownership and the launcher returned its real bus address. Thus changing to a launcher-generated accessibility bus **alone** did not reproduce the #415 construction behavior.

## Critical evidence boundary

The chrooted D-Bus daemon cannot inspect host `/proc`, so `GetConnectionUnixProcessID` returns `UnixProcessIdUnknown` for outside clients. This is not hidden. Candidate cases therefore resolve exactly one accessible root named `org.inkscape.Inkscape` on their private per-case accessibility bus and record `pid_attribution_available=false`; baseline cases retain PID binding. This experiment is about path lifetime, not production attribution semantics.

The private chroot is an isolation shim, not a stock installed desktop: its accessibility config lowers connection limits because the container hard `NOFILE` limit is 16384 while the daemon tries 65536, and `/dev/null` is a regular-file substitute because device-node creation is prohibited. The official launcher and Registry binaries are exact retained Debian-package bytes. These constraints limit scope.

## Interpretation

**Fact:** all six sessions retained readable A/B paths through panel close and exact path/name continuity after reopen.

**Inference:** Registry presence, listener registration, and launcher-generated accessibility-bus lifecycle/configuration are each insufficient individually to explain the #415 construction's path defunct observation.

**Not tested:** application-side session `org.a11y.Bus` discovery, exact standard desktop startup ordering, combined timing/churn interactions, or selection-event identity itself.

## ERROR CHECK

Frozen audit passes six first outcomes with zero errors. Six post-measurement corruptions are rejected: changed path equality, wrong target name, missing Registry owner, held final key, erased launcher PID-attribution boundary, and arm mismatch. Fresh archive reconstruction reruns the audit; these are not extra live samples.

## Next single question

Do not take #415's live selection-event allocation. If #415 formal measurement confirms path defunct/reincarnation, the remaining high-information mechanism is application-side **session `org.a11y.Bus` discovery / full standard startup integration**, or exact timing interaction. That rung requires isolation that does not write shared `/etc`; do not fake the service path.
