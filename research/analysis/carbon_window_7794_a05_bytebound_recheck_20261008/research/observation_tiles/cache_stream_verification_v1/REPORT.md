## 5. 作業割当の測定と読み取り内容

時間測定とは別に、ファイルを変更しない1回の検証でtracemallocを開始・終了した。
値はPythonで追跡された割当のピークであり、RSSやPNGエンコーダの全メモリではない。
フレームの既存メモリ、OSページキャッシュ、C側全割当はこの指標で比較していない。

| PNG長 | FULL_PINピーク［最小–最大］B | STREAM_PINピーク［最小–最大］B |
|---:|---:|---:|
| 197,173 | 198,858［198,858–198,858］ | 67,754［67,754–67,754］ |
| 307,963 | 309,648［309,648–309,648］ | 67,754［67,754–67,754］ |
| 923,404 | 925,089［925,089–925,089］ | 67,754［67,754–67,754］ |

大画像の対応ピーク比0.073241は事前条件0.25以下を満たした。一定の測定値はこの
CPython実装・コード・条件での結果であり、他の環境での同一バイト値の保証ではない。

さらに別の計画済み検証で、全read/readinto要求長・戻り長・hash.update入力総量を保存。
すべてのSTREAM検証は65,536 B以下の要求で、923,404 Bのファイルでは全923,404 Bを
ハッシュした。最後に1 BのEOFプローブを実施し、追加データがないことを確かめた。
大きい画像を部分照合した結果ではない。FULL_PINも同じ全長・同じdigestを得た。

4MiBは新候補の設定上の対応上限、64KiBは作業バッファ上限であり別物である。
今回の実測最大PNGは923,404 B。4MiB全域、ハード時間期限、巨大画像対応を検証した
とはしない。未知・上限外の長さは構築テストで読取り前に拒否することを確認した。

## 6. 保守条件と正確性

noise640の7条件・3方式・2反復、42ケース。条件が完了してから検証するため、同時
書込み中の一貫性やチェック後の変更は対象外。Candidateは条件名を受け取らず、
現在のFrame、保存済み長さ・digest、実ファイルだけで判断する。

| 条件 | FULL_PIN／STREAM_PINで両反復に確認した結果 |
|---|---|
| キャッシュ欠落 | 新しい正確なPNGを生成。その次は再利用 |
| 切詰め | 長さ不一致で再生成。その次は再利用 |
| 同じ長さの末尾変更 | 256KiBより後の変更もdigest不一致で再生成 |
| 可逆な別エンコード | 画素が同じでもバイト契約上は再生成。その次は再利用 |
| 現在フレーム変更 | 新しい要求画素を公開し、新しいpinを登録 |
| 次の出力名が占有済み | FileExistsErrorで拒否。元のsentinelを上書きしない |
| 末尾データ付加 | 長さ不一致で再生成。その次は再利用 |

この有限条件では、バイト照合の正しさを維持したまま再利用可能領域を広げた。
画素同一性で別エンコードを再利用するPIXEL_CHECK_REPAIRとは契約が異なるので、
今回の候補をその代替として同等と呼ばない。

## 8. 条件付き論証、ERROR CHECK、次の統合判断

PLAN.mdに変数表、readintoループの帰納的不変条件、単位チェックを記載する。
Pythonのhash.updateは分割の結合と同じdigestを定義する。しかしdigest一致は一般に
バイト同一性の数学的証明でも真正性証明でもない。一般利用には衝突耐性と信頼する
初期pinを仮定する。この有限実験では別実装の全画素比較も実施した。

ERROR CHECK：8回合計と初回を分離。内側sink時間と外側wrapper時間を加算しない。
最小値・中央値・最大値を同じ5反復から計算。tracemallocは別パス・別指標。
全バイトの読取りと照合、全87ケース、6件の意図した拒否を除外しない分母を再構成。
旧ソースと旧データは変更なし。公開文案はremote Issue/PRの代わりにはならない。

次に変更しうる設計判断は、**画像サイズ上限と検証作業バッファを別の設定として持つ**
こと。実配送経路へ組み込む前に、保存所有権、変更のない検証区間、対応サイズ、
unsupported時の返却、初回を含む全コストを明示して検証する必要がある。
これは無制限の上限解除や、存在チェックだけへの復帰を勧める結果ではない。
