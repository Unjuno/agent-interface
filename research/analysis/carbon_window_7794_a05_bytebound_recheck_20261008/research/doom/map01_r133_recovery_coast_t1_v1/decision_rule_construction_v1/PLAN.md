# Direction-sensitive paired T1 adjudicator — host construction experiment

Status: `FROZEN_HOST_CONSTRUCTION`. This addresses the preregistration defect noted on #59 by comment #5921728502. It is not the #59 live experiment, not authorization, and not a claim that the proposed endpoint proxies are scientifically sufficient for all MAP01 states.

## H / T / D / C / U

- **H:** A deterministic three-pair adjudicator that separates instrumentation/release integrity from comparative evidence will never label equal, mixed, or coast-favoring paired outcomes as a directional PASS; it will PASS only when recovery strictly wins both preregistered endpoints in at least 2/3 pairs and loses neither endpoint in any pair.
- **T:** Freeze an executable host-only rule and an independently authored oracle. Exhaustively enumerate all 729 combinations of three paired progress signs × three paired conservative-exposure signs; then exercise fixed input-integrity, threat-absent, no-useful-event, release-harm, stale-action, mismatch, and duplicate-inventory controls. Candidate and auditor run once each, with no Docker, X11, model, game, GUI, input, or GitHub writes during either invocation.
- **D:** `PASS_T1_DIRECTIONAL_ADJUDICATOR_CONSTRUCTION` iff all 729 candidate decisions match the separate oracle; only the exact predeclared joint-direction patterns return `PASS_DIRECTIONAL_FIXTURE_SCOPED`; joint opposite-direction patterns return `FAIL_DIRECTIONAL_FIXTURE_SCOPED`; every tie/mixed/overlap pattern returns `UNCERTAIN`; no threat or no useful event returns `HOLD_NOT_EVALUATED`; unsafe release/stale action returns `FAIL_SAFETY`; identity/order/completeness faults return `STOP_INTEGRITY`; and every frozen control is rejected/classified as specified. This verifies code against this proposed rule, not the rule's empirical validity.
- **C:** CPython 3.12.3 on WSL2/Linux x86-64; standard library only; synthetic paired records. No shared compute or experiment allocation.
- **U:** A host construction check for adjudication logic only. It establishes no threat detection validity, score accuracy, exposure reconstruction, plan/action lineage, MAP01 recovery efficacy, safety rate, population effect, or authorization. Three pairs remain descriptive and fixture-scoped.

## Proposed T1 estimands (must be read back into the live freeze)

- **Arm/order:** three restored matched pairs in the fixed sequence recovery→coast, coast→recovery, recovery→coast. No reseeding, replacement, or posthoc pair exclusion.
- **Start match:** exact fixture/WAD/image/model-contract identities; same seed/map/skill; equal game tic, starting health/ammo/kill/death counters, and SHA-256 of the first ready frame within each pair. A mismatch is `STOP_INTEGRITY`, not a tolerance adjustment.
- **Clock/horizon:** session time origin is the monotonic timestamp of the accepted ready handshake after the first scorer baseline. The observation horizon is 60,000 ms or earlier terminal death/exit. A fixed enemy-visible ready frame confirms the designated threat-contact exposure; conservatively treat the nonterminal portion of the entire 60-second horizon as threat-active, even if the enemy later leaves view. This is a fixed exposure-window assumption, not a claim of continuous enemy presence.
- **Useful-outcome oracle:** independent game-state scorer computes `(map_exit, alive_at_horizon, -death_count_gain, kill_count_gain)` and compares lexicographically; `map_exit` is 1 only for a finished-alive episode before the frozen timeout guard. Kills/deaths are exact counter deltas. A positive useful outcome exists iff `map_exit` or `kill_count_gain > 0`. Health loss and ammo use are retained as secondary outcomes, not silently folded into a weighted score.
- **Unsafe-unprotected exposure:** within the fixed threat-contact window, protection exists only while the frozen guard is valid and current and owner/XQueryKeymap evidence confirms at least one preregistered protective key physically down under an unexpired lease. Everything else is unprotected. Reconstruct a conservative duration interval `[lower_ms, upper_ms]` from the independently audited input-state observations and owner-thread KeyRelease→XSync brackets; each explicit UP needs an identity-bound bracket and before/after keymap state. Never substitute admitted-program envelope duration for actual input state or impute an absent release time. For each pair, recovery clearly improves exposure only if `recovery.upper_ms < coast.lower_ms`; it is clearly worse only if `recovery.lower_ms > coast.upper_ms`; overlap/equality is unresolved/tied.
- **Separate instrumentation gate:** `PASS_INSTRUMENTATION_AND_RELEASE` only with all six sessions complete/audited, exact fixture/source/model/seed/map/skill identities, exact pair/start identities and order, bound exposure intervals, every explicit key-up bracket plus keymap evidence, no stale action after invalidation, and 3/3 verified neutral terminal releases per arm. Missing owner-thread release brackets or keymap rows are `STOP_INTEGRITY`. Threat absence is recorded and makes the comparative result HOLD, not an instrumentation failure. Any nonneutral/unverified release or stale action is `FAIL_SAFETY`; provenance/order/inventory/audit gaps are `STOP_INTEGRITY`. This does not imply a comparative pass.
- **Comparative rule:** with instrumentation PASS and at least one positive useful outcome somewhere, `PASS_DIRECTIONAL_FIXTURE_SCOPED` iff recovery wins useful-outcome ordering in >=2/3 pairs and loses in 0/3, and clearly lowers unsafe exposure in >=2/3 pairs and is clearly worse in 0/3. `FAIL_DIRECTIONAL_FIXTURE_SCOPED` iff coast wins both endpoints in >=2/3 pairs and recovery wins neither endpoint in any pair. All other complete outcomes are `UNCERTAIN`. If no threat exposure occurs in either arm or no positive useful event occurs anywhere, comparative disposition is `HOLD_NOT_EVALUATED` while instrumentation may still PASS.

These estimands are an explicit proposal for future review. They must not be silently assumed to amend #5085's pending request; the exact live candidate, image, exposure-state logger and owner-release evidence still need source freeze and authorization.
