# Durable caller resumes after a real GUI command write

The frozen durable_submit_v1 journal was exercised on an unchanged actual Inkscape/cause-servo socket runtime, seed233. The scripted parent selected the rectangle, received a correlated clock, and initialized the journal from the latest received continuation. A separate worker submitted one generated-identity program to set X96 and save. Its transport callback performed an actual AF_UNIX sendall, recorded zero received-response bytes, and called os._exit(17) without receiving a reply. Kernel process exit closed its socket and released its flock. At exit, server receipt was explicitly unknown.

A second worker attempted another submit through the same journal and was refused before any transport call. A third worker read the journal and performed one command-free read on the same socket; it recovered the original exact command echo, admission, observations and completed/released terminal. It committed the new continuation and cleared the pending operation. No input program was resent. The parent verified the same bridge PID live before the crash, after the crash, after the blocked worker and after recovery; it issued finish only after reconciliation, then observed exit0 and removal of both socket paths. Runtime events independently establish the original program completed. No runtime restart occurred in this harness.

The49-event trace has exactly two accepted programs: initial selection and the generated journal action. The latter is echoed once and contains one Ctrl+S step. All9 image frames reconstruct exactly. The assistant viewed final image009 after execution: X96,Y50,W40,H30 and Document saved. Independent SVG parsing confirms those values and no transform. SVG SHA256:9ee7452bd3c14b16b9ded9e353f21f307fdc160168fb3b2fc76030ba71b4e616.

`audit_durable_inkscape_v1.py` checks pinned caller/runtime sources, all returned event slices against the runtime trace, received continuation replay, unchanged pre-crash continuation, persisted exact request, wire hash, three distinct worker PIDs/exits, command-free recovery, exact reconciliation, unique accepted/echoed operation, input release, live bridge checks, image bytes, SVG and cleanup. Results: results/durable-inkscape-01. The loss fixture, blocked worker and recovery worker exited17,0,0; the supervisor exited0.

Linux perf_counter measurements: send completion to recovery-worker exit852.546611ms; recovery-worker wall702.152829ms. These include process startup, application execution/waiting, file persistence and supervisor overhead. This is one scripted recovery case with no matched baseline, no model call, and no human-tempo or throughput claim. It is deliberate process loss after a successful local send, not an organic network outage, partial write, runtime crash or power-loss experiment. Storage is the WSL-mounted Windows repository. No claim of filesystem power-failure durability is made.

The journal is a cooperating single-writer candidate, not default session authority. Another client or a new journal can bypass it. Clock/finish remain explicit parent operations outside this submit-only wrapper, issued here only when no pending journal operation exists. Rejected runtime outcomes still lack operation identity and remain unresolved; a crash before any actual send can also remain unresolved indefinitely. Event-ring gaps and channel closure cannot prove execution or process termination. Failure-only harness cleanup terminates its bridge and is not a production supervisor.

Next make rejected outcomes attributable to exact request/action identity and verify that a stale/refused request can be reconciled without allowing a duplicate input. Do not expand into automatic retries or reset uncertainty by elapsed time. This actual process-loss result is separate from the prior injected archived-reply test and does not promote either into a general performance claim.
