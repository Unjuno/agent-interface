# Exact ROI predicate cost at fixed bytes

Task `QUIET-WATCH-PREDICATE-COST-20260916-001`, Issue #252.

**Disposition: `PASS_COST_SCOPED`.** This promotes only the primitive claim that an exact native CPython bytes-in/count-out implementation is materially cheaper than the existing Python byte loop on this frozen offline corpus. It does **not** promote shared runtime code and does not establish a live-watcher, X11 acquisition, scheduling, release-latency or arbitrary-GUI speedup.

## Why this rung exists

Issue #236 retained `HOLD_COST_GATE` for native XGetImage acquisition at fixed 2 ms polling. The acquisition-path intervention preserved detection/safety but missed its frozen 20% cost threshold. The next smallest discriminator is therefore the remaining per-ROI predicate loop, with acquisition removed entirely.

## Frozen question

Both arms receive the exact same immutable 4096-byte 32x32 BGRX `bytes` object and return the exact count of pixels whose first three bytes equal BGR `(50, 50, 220)`. The threshold semantics remain `count >= 512`.

Baseline: the existing Python loop, including a three-byte slice comparison once per pixel.

Candidate: one CPython C-extension call over the same `bytes` object, exact full count, no early threshold exit, no ROI shrink, no subsampling, no predicate change.

The source-first freeze was recorded in Issue #252 before timing. GitHub blob identities at the frozen head are retained in the strict posthoc audit.

## Corpus and schedule

The corpus contains 512 deterministic frames generated byte-exactly from SHA-256 counter streams. The first frames explicitly cover count boundaries 0, 1, 2, 255, 256, 510, 511, 512, 513, 514, 768, 1022, 1023 and 1024; remaining counts are deterministic across 0..1024. Accidental random exact target pixels are removed before target locations are inserted. Corpus SHA-256 is `90c59c47424b08bee13012e6f95155c67f4c0744687d80c41ade9e4ee822d498`.

Correctness-only preflight, before timing: 512/512 expected, Python and native counts agree; zero threshold mismatches; short, long and wrong-type native inputs reject.

Formal measurement is one block of 16 paired comparisons. Each arm evaluates 512 frames for 16 passes = 8,192 evaluations per pair, 131,072 evaluations per arm across the block. Pair order alternates Python→native / native→Python. Both arms see the same deterministic frame order inside a pair. Two corpus passes per arm are warmup and are not timed. No retry, extra pair or threshold change occurred.

## Formal first outcome

| Endpoint | Python loop | Native extension |
|---|---:|---:|
| median wall per evaluation | 70,420.133 ns | 768.754 ns |
| median current-thread CPU per evaluation | 70,417.243 ns | 768.547 ns |

Median paired candidate/baseline ratios:

- wall: **0.010873862866400373** (~91.96× reciprocal reduction factor)
- current-thread CPU: **0.010873172951172873** (~91.97× reciprocal reduction factor)

The frozen promotion gate required both ratios `<= 1/3`; both pass by a wide margin. All 512 exact counts and all >=512 classifications agree.

Observed paired-ratio ranges:

- wall: 0.0098652 .. 0.0118616
- current-thread CPU: 0.0098639 .. 0.0118585

Posthoc, non-gating bootstrap 95% intervals for the paired median are retained in `posthoc_uncertainty.json`: wall [0.0105611, 0.0110094], CPU [0.0105590, 0.0110076]. These intervals characterize this finite block only.

## H / T / D / C / U

**H:** moving only the exact target-count loop into a native CPython extension preserves every count/classification and lowers both paired wall and current-thread CPU cost to at most one third of the Python-loop baseline.

**T:** deterministic 512-frame byte corpus, one source-frozen 16-pair offline block, identical bytes for both arms, single-CPU affinity, exact count comparison, no GUI/X11/model/game/input path.

**D:** `PASS_COST_SCOPED`. Semantic equality is 512/512 and both cost ratios are ~0.01087, below the frozen 1/3 gate.

**C:** the large difference includes Python interpreter/slice allocation versus native loop and CPython extension-call overhead. It does not imply that the complete watcher improves by ~92× because XGetImage, scheduling, copying, cancellation and rendering are absent here. Compiler auto-vectorization/cache effects are also part of this implementation result.

**U:** one virtualized AMD host, one CPython/GCC build, unpinned frequency, hot repeated corpus, finite paired block. Primary empirical dispersion is retained as the 16 paired ratios. For a normal-approximation descriptive mean-ratio uncertainty, `posthoc_uncertainty.json` retains standard uncertainty and expanded uncertainty with `k=2`; the preregistered decision used the median, not this posthoc uncertainty calculation.

## Audit correction retained, not hidden

The frozen `audit.py` correctly rejects count and final-decision mutation but was found post-measurement to omit two integrity checks: it did not recompute `wall_ns_per_eval` / `thread_cpu_ns_per_eval` from raw duration and `n`, and it did not use raw durations directly for all summary reconstruction. Negative controls demonstrated that a raw-duration-only mutation and a derived-per-evaluation-only mutation could escape the frozen audit.

No measurement was rerun and the frozen audit/result were not edited. `audit_strict_posthoc.py` is an additive independent posthoc audit. It checks the five frozen Git blob identities, regenerates the corpus independently, checks all counts, pair/order/n/checksum structure, recomputes per-evaluation fields from raw durations, reconstructs all summary values and decision, and requires a recorded pinned CPU. It passes the original result and rejects all four retained negative mutations: native-count, decision, raw-wall-only and per-eval-only.

Thus the formal first outcome remains the one measured block; the stronger audit repairs evidence validation only.

## Next single question

Do not optimize the predicate further yet. The primitive cost gate is decisively passed. The next informative rung is a separately frozen integration test that holds the native acquisition implementation fixed and changes only where the exact count occurs: Python predicate after acquisition versus the same native count composed into the acquisition path. Measure full acquisition+predicate wall/CPU and live sampling gaps while preserving the existing 2 ms schedule and safety semantics. This is necessary before claiming any live-watcher benefit.
