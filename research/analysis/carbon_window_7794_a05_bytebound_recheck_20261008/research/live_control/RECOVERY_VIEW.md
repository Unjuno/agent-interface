# Recovery result exposes resolution, channel and input state separately

recover_once_v2 attaches a recovery-view-v1 presentation to the unchanged raw request/reply/state from recover_once_v1. The view provides status, read action identity, channel state, new-input constraints, suggested next inspection, full pending data, resolution for this read action, separately labeled historical resolution and the latest received observation. Task completion remains explicitly unscored, and an observation is not described as fresh or proof of target identity. The underlying single-read behavior and journal admission rules are unchanged.

`resolved` means no pending command and a terminal/rejection in the validated durable result matches this read's action ID. It does not mean task success. An old resolution for a different action yields `no_pending` with no resolution_for_read_action, rather than false current success. A pending command yields `unresolved`; closed-channel state is a separate axis. Even a resolved command may coexist with a closed channel, in which case new input is blocked. A channel that has not reported closure is not claimed to be currently live. Unresolved conflicts suggest evidence inspection; unresolved non-conflicts require an explicit read or inspection. Neither hint executes anything.

This function consumes validated local durable results; it is not a validator of arbitrary fabricated events or a new source of input authority. Existing durable reconciliation checks exact request echo, admission and released terminal before clearing pending. The view only correlates the resulting action-scoped resolution. Clock reads without action IDs are not labeled action-resolved. Output objects are copied so modifying a displayed observation does not mutate caller state.

Offline controls repeat timeout, closed, read error, conflicting echo, matched reply and no-pending transport cases through v2. They check displayed pending/channel/input status and preserve prior blocking guarantees. Four presentation controls check input immutability, output non-aliasing, old-resolution mismatch and resolved-plus-closed separation. Transport errors/no-pending still propagate exceptions without a view; this change does not wrap every error into a uniform response. Results are in results/recovery-view-controls-01.

A fresh Inkscape seed239 experiment directly supplies this returned recovery view as the model's evidence, replacing the driver's handwritten pending/resolution summary. After the same scripted edit/save and intentional response abandonment, one caller read resolves the original request in0.806s. The responder then requests independent verification of X88,Y50,W40,H30; saved SVG verifies. There is no model retry, GUI replay or manual correction. One model call uses10405 input tokens (6912 cached),141 output and7.579s runner time. The preceding handwritten-summary episode used9516 input and6.948s. This view increases input by889 tokens in these separate episodes; no compression or latency improvement is claimed. Full observation and historical evidence are retained for clarity rather than optimized token count.

Audit checks exact prompted view against the presentation function, measured source hashes, continuation/journal/event replay, one original edit echo/Save, raw model output and matching image, both released terminals and independent SVG. All49 events,9 exact transported frames and9 append records agree. Driver exits0, sockets removed, no error artifact. Evidence is results/recovery-view-ink-01; run audit_recovery_view_ink_v1.py under Linux for read-only replay. Initial edit remains scripted and the model verifies only; one live resolved case does not prove model handling of every failure view.

Decision: retain this opt-in response shape for subsequent caller experiments, with original raw evidence intact and no general-default promotion. It improves access to the states a caller must distinguish, at a measured input cost. Next use the returned state to choose a genuinely new bounded action after recovery in a multi-step task, with fresh admission and independent scoring; currently only verification follows. Do not spend further turns on cosmetic status fields or repeated successful recovery screenshots. Full autonomous live interaction and broader domain coverage remain unfinished.
