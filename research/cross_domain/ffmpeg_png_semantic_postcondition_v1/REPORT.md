## Question

Issue #423 showed on a generated JSON fixture that exact bytes can be a sound but over-strict postcondition when the requested outcome is representation-insensitive. This transfer uses actual PNG files produced by installed FFmpeg 7.1.5 and keeps Git entry kind/mode, output-only write scope, unrelated-state preservation and final current-OID CAS fixed. Only the content predicate changes:

- `exact_file_bytes`: require byte-for-byte equality to the frozen canonical PNG;
- `decoded_pixels`: decode the PNG and require exact 96x64 RGB bytes equal to the frozen target.

The declared task intentionally treats lossless PNG compression/filter representation as irrelevant. It does not ignore geometry or pixel differences.

## Interpretation

For this declared pixel-exact but encoding-insensitive image outcome, exact PNG file bytes are too strict. Exact decoded dimensions and RGB bytes admit native FFmpeg outputs that differ only in lossless PNG representation while continuing to reject the authored pixel/geometry/corruption controls and preserving the Git publication race barrier.

The result does not say that PNG metadata, alpha, profiles, bit depth or exact encoding are always irrelevant. A real task must state which artifact properties constitute the postcondition. The narrower architectural point is that postcondition strength has two dimensions: it must include all semantically relevant properties, but it should not accidentally elevate irrelevant representation details into required semantics.
