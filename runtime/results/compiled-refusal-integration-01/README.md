# Compiled pre-input refusal integration

Source at intake: main 673763554192ae26636e07d5a48f03b3cd7fb044. This fixes a concrete #57/#52/#55 integration correctness boundary in the existing portable compiled graph/X11 adapter. It is not another control architecture, a new sensor, or a live GUI efficiency trial.

The adapter rechecks association after admission and can return status=refused/input_dispatched=false when binding changes before execution. It has no release receipt because it never sent input. Previously the adapter dropped input_dispatched and the graph classified release_verified=false as RUNTIME_FAILED/execution_failed. That conflated a pre-input abstention with an actual input-release failure. It can cause callers to attribute infrastructure/recovery cost to an eligible safe stop.

The graph now accepts one OPTIONAL strict-boolean input_dispatched terminal field. Explicit status=refused/input_dispatched=false with no reported held keys/buttons returns SAFE_YIELD/execution_refused, retains the actual release_verified=false event and completed verified prefix, and sends no subsequent observation/action. It does not invent a completed action, effect, neutral release or permission to replay. Existing terminal shapes keep their previous semantics. False cannot accompany completed/uncertain status; malformed flag values are rejected. True/unknown delivery, held input and actual release failure keep the stricter existing paths.

The X11 adapter forwards native no-input evidence only without execution metadata or unresolved recovery. It retains the full raw receipt regardless. A declared no-new-input event cannot hide previous input needing recovery; two additional regressions exposed that boundary before its fix. No guard, deadline, one-use authorization, alias freshness or STOP/reset rule was relaxed.

They exercise association change after first and second admission, native zero-input refusal, retained completed prefix, no further inputs, actual release/recovery uncertainty, held keys, absent/malformed/contradictory no-input flags, uncertain delivery, budgets, scope changes and existing successful effect-dependent continuation. Fake captures/input are used; no game/GUI/model or physical release claim follows.

RED: three adapter cases fail with old RUNTIME_FAILED/execution_failed; optional-field cases fail old strict terminal validation. red.log retains all results. First GREEN's test-only terminal-name lookup omitted the .json suffix (IndexError); corrected without changing runtime behavior and retained in green.log/green-corrected.log. Two additional RED cases showed that propagating no-input through native release/recovery failure was too permissive; red-release.log retained, then the adapter gated that propagation. green-final.log and green-optimized.log retain the initial 44-test passes. A final review added a contradictory no-input/positive-emission/no-release case: red-execution.log fails, then the adapter conservatively stopped forwarding no-input evidence whenever execution metadata exists. green-hardened.log and green-hardened-optimized.log pass all 45. No historical experiment result was modified or reclassified.
