# Experimental bounded idle observation (not qualified)

This draft exposes a separate read-only idle capture in the Python guarded owner and its owned-process RPC. It uses a dedicated single-capture cancellation scope. Its candidate stages the returned frame, then orders sequence commitment against cancellation acknowledgement. Expiry and cancellation retire the read worker and require review; the worker may remain blocked until its dependency returns. The existing synchronous `observe` and public MCP tool are unchanged.

The method requires an already open owner with the existing process-identity, target-query and observation-worker options. The deadline uses the same host's monotonic clock. The draft refuses lifecycle mode and a generic multi-stage cancellation scope. It is not a hard end-to-end time bound: a daemon thread owns the blocking `recv`; owner startup, scheduling, response processing, lock contention and cleanup may outlive the deadline. `review_required` does not prove physical release. The single-capture scope is not yet fenced against every possible owner/session or direct backend operation; staged history can be visible to unsupported concurrent direct bridge readers. A dedicated scope must not be reused for a later task. Do not use this candidate as production authority.

Local Fake X tests cover healthy acquisition, timeout, cancellation, late worker response, cancellation/commit ordering, guarded keyboard and window activation scope misuse, and actual spawned-owner RPC. The existing owner/process and observation-worker tests also ran. These are not real-X, WSLc, provider, physical-release or application-effect qualification for the owned-process API. Earlier private-Xvfb experiments tested a bridge-only predecessor, not this owner RPC.

Before considering merge: design and test a bounded parent transport and process-retirement policy with explicit uncertain outcomes; enforce exclusive ownership for every relevant entry point; address staged-history visibility and lifecycle identity; establish full retained evidence and end-to-end feedback; test actual Xvfb and cancellation/cleanup including independent input and task effect. Retain no replay on unknown and do not infer application success from a frame.

At predecessor `70243bd`, an owned-process Fake X fixture paused the child **after** frame commitment but before its RPC response; the parent waited past the deadline and later accepted `observed`. The current candidate delegates full framed receive to a daemon thread, quarantines the owner at expiry, and refuses a late response before applying its snapshot. Quarantined close retires the exact owner without an unfenced release and reports cleanup UNKNOWN; child death is not proof of release. Targeted Fake X tests cover the original delayed response, a late control snapshot, and this no-release close. This is a prototype, not a physical-release or hard-deadline guarantee. The receiving thread, child, server-side requests, and held inputs may persist until explicitly handled; further response/cancellation/close races, simultaneous calls, partial transport frames, retention failure and real-X behavior remain unqualified.

At predecessor `cfb9adf`, two Fake X tests with simulated control timing found that cancellation starting after quarantine, or starting before expiry but returning after it, could reach `_cleanup_after_owner_retirement`. The tests replaced that cleanup with an exception and did not emit a real release. The current candidate reserves idle-observation and cancellation state under a short parent lock: an ordinary in-flight cancellation prevents starting idle observation, and a cancellation started during idle observation uses a no-cleanup path even if its response arrives after the parent deadline. Invalid or unconfirmed responses quarantine the session. New owner RPCs are refused while cancellation replies remain in flight. Tests cover both orderings and late successful/failed control responses; the previously failing test now passes. The design still requires deeper review of all operation-entry, close and cancellation interleavings, held-input custody, partial-frame and native-I/O behavior. These tests neither prove nor disprove a real late release.

Close now returns `cleanup_deferred` / UNKNOWN without attempting release while an idle capture or its cancellation remains in flight; it does not cache that deferred receipt, so a caller may explicitly close later. Once close starts, a new idle capture is refused. If the control response never completes, this is not finite cleanup and must not be reported as release. The same lock cannot prevent arbitrary native calls already in progress, and the implementation remains draft pending real transport and input-custody tests.
