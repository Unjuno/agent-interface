# Experimental bounded idle observation (not qualified)

This draft exposes a separate read-only idle capture in the Python guarded owner and its owned-process RPC. It uses a dedicated single-capture cancellation scope. Its candidate stages the returned frame, then orders sequence commitment against cancellation acknowledgement. Expiry and cancellation retire the read worker and require review; the worker may remain blocked until its dependency returns. The existing synchronous `observe` and public MCP tool are unchanged.

The method requires an already open owner with the existing process-identity, target-query and observation-worker options. The deadline uses the same host's monotonic clock. The draft refuses lifecycle mode and a generic multi-stage cancellation scope. It is not a hard end-to-end time bound: the parent RPC still uses blocking `recv`, owner startup is outside the deadline, and runtime scheduling, result transport and cleanup may outlive it. `review_required` does not prove physical release. The single-capture scope is not yet fenced against every possible owner/session or direct backend operation; staged history can be visible to unsupported concurrent direct bridge readers. A dedicated scope must not be reused for a later task. Do not use this candidate as production authority.

Local Fake X tests cover healthy acquisition, timeout, cancellation, late worker response, cancellation/commit ordering, guarded keyboard and window activation scope misuse, and actual spawned-owner RPC. The existing owner/process and observation-worker tests also ran. These are not real-X, WSLc, provider, physical-release or application-effect qualification for the owned-process API. Earlier private-Xvfb experiments tested a bridge-only predecessor, not this owner RPC.

Before considering merge: design and test a bounded parent transport and process-retirement policy with explicit uncertain outcomes; enforce exclusive ownership for every relevant entry point; address staged-history visibility and lifecycle identity; establish full retained evidence and end-to-end feedback; test actual Xvfb and cancellation/cleanup including independent input and task effect. Retain no replay on unknown and do not infer application success from a frame.

An owned-process Fake X fixture now pauses the child **after** it has captured and committed a frame but before its RPC response. A characterization test verifies that, after the deadline, the parent stays blocked and then returns `observed` when the child resumes. The prospective test `test_parent_discards_response_delayed_past_observation_deadline` deliberately fails: the parent is still waiting after the deadline. This is a reproducible failure of this draft, not an assertion about the unmodified main API. Do not merely add `poll()` and claim a hard bound: readiness can precede completion of a framed message, and owner retirement/late-response disposal must preserve input-custody uncertainty and never allow an unqualified later release to affect a newer client.
