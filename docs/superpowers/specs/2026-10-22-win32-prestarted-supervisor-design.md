# Win32 Prestarted Supervisor for Bounded Input Recovery

**Status:** Design proposal for review
**Scope:** Win32 input-operation ownership and bounded recovery
**Decision requested:** Approve, revise, or reject the proposed falsifiable prototype before a separate implementation plan is written.

## Context and outcome

The required outcome is a bounded cancellation response **and** bounded input neutralization while an input API call is blocked, followed by independent platform-state readback and an independently checked task effect on a fresh target. A bounded return by itself is not release. Until each property is observed, the operation result remains `UNKNOWN`, replay is denied, and no new input operation may overlap a producer whose retirement is unresolved.

Current `Win32RuntimeSession.dispatch()` and `Win32Backend.execute()` call `SendInput` synchronously. The backend records a held-key obligation only after `SendInput` returns; `recover_input()` refuses before attempting release unless `recovery_required` is already true. The accepted-before-return packet and the later [before-acceptance public-recovery packet](../../../research/integration/win32_before_accept_blocked_recovery_20261022_r01/README.md) both reproduce blocked-call schedules with an inert fake: bookkeeping says recovery is unnecessary, public recovery refuses without UP, and the old producer can still accept DOWN after recovery returns. The latter confirms the source-derived schedule for that test double; neither packet is a captured native Windows outcome.

Microsoft documents `SendInput` as inserting events serially into the keyboard or mouse input stream and returning the inserted count. Its documented signature exposes no target desktop/session, deadline, or cancellation handle. The serial-insertion guarantee orders events submitted through that API; it does not establish cancellation, a bounded return, or fencing against a different process. Windows desktop objects have access controls and window-message boundaries, while only the active desktop of an interactive window station receives user input; those facts do not establish that a non-active/private desktop confines `SendInput` events. Microsoft documents `TerminateProcess` as asynchronous and requires waiting on the process handle to confirm exit; its pending-I/O language does not establish whether an in-flight `SendInput` maps to pending I/O or whether an accepted input event can take effect after producer exit. These uncertainties remain explicit test gates ([`SendInput`](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-sendinput), [`Desktops`](https://learn.microsoft.com/en-us/windows/win32/winstation/desktops), [`Window Stations`](https://learn.microsoft.com/en-us/windows/win32/winstation/window-stations), [`TerminateProcess`](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-terminateprocess)). `SendMessageTimeout` is not a substitute: it applies to window-procedure messaging, and its timeout can be ignored for same-queue calls; it does not wrap or cancel `SendInput` ([`SendMessageTimeout`](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-sendmessagetimeouta)).

There is a separate target-generation and standard-caller integration gap in the current Win32 path. Direct [`Win32RuntimeSession.dispatch()`](../../../runtime/backends/win32_v1/session.py) admits observation sequence and binding revision but exposes no target-guard argument. The opt-in [`MoveBridge`](../../../runtime/guarded_win32_v1/bridge.py) supplies a `BoundView` adapter that does forward `bound_target`, a preflight binding guard, and a per-operation guard to [`Win32Backend`](../../../runtime/backends/win32_v1/backend.py). Those checks cover the retained observation/binding revision, HWND/geometry/focus and pixel digest; they narrow stale-reference risk but do not pin or verify the HWND owner's PID and process-creation identity. The bridge is a private Python API, not the selected public standard MCP caller. Thus the existing bridge has useful local freshness checks, while target-process generation evidence is not yet carried end to end through the standard caller.

## Candidate design

A prestarted supervisor is the sole parent-side owner of operation state. Its deadline-critical coordinator must not call an API or wait whose return is unbounded. In particular, operation-child creation and pool replenishment run outside that coordinator, or the supervisor keeps an already-started operation-worker slot available. The coordinator can continue accepting cancellation and status requests if process startup stalls. Each child is bound to one operation ID and a one-use admission capability with a fixed expiry; the child may submit no input until the coordinator confirms readiness and admits that capability. A child that starts late or receives a stale capability must exit without input. If neither a nonblocking startup path nor an already-ready slot is available by the admission deadline, the operation remains unstarted and fails closed.

The admission capability also pins the selected target generation: registered HWND, owning PID and process-creation identity, observation sequence, binding revision, observation digest, and absolute expiry. The coordinator must reject missing or stale identity evidence, and the operation child must recheck the pinned generation immediately before every consequential input operation. A changed or unverifiable generation denies task input and requires fresh observation/authorization. This check narrows but does not eliminate the race between identity readback and `SendInput`; the design makes no atomic capture-to-input claim. The global recovery sender uses only the held-input obligation and never focuses or targets a newly selected window.

For each admitted operation, a disposable child performs at most one input program and reports through bounded IPC. On cancellation or expiry, the supervisor closes admission for that operation, retires that exact child, and waits only until a fixed deadline. It records retirement as confirmed or unknown. Child creation, readiness, admission, cancellation, retirement, and IPC each have distinct timestamps and deadlines; a bound on one is not evidence for another.

A distinct, prestarted recovery process may submit compensating UP events only after the operation producer's retirement is confirmed. An independent observer then reads key and button state. If retirement or readback misses its bound, the supervisor returns `PENDING` or `UNKNOWN` to the caller within its response budget, denies replay, and keeps new input fenced. This response is not proof of release; if the caller's required outcome is confirmed neutralization by that budget, the candidate fails qualification. A bounded caller response never authorizes another sender while the prior producer remains alive or its retirement is unknown.

## Custody, compensation authority, and quarantine exit

**Q01 — custody before `SendInput` returns.** Before it can grant input, the supervisor derives a finite superset of every key and button the admitted program may put down. It rejects programs whose possible-down set cannot be derived. It records the operation ID, child identity, target-generation capability, mapped key/button set, baseline-state receipt, and expiry in an append-only journal and flushes that reservation before acknowledging admission. A bounded journal-writer worker performs the flush; a stalled/failed flush yields no admission capability, while the coordinator remains available for cancel/status requests. The child cannot enter `SendInput` until it receives that one-use acknowledgment. If the API call returns, its inserted count refines the receipt but never removes a possible-down obligation by itself. If the child exits or loses IPC after acknowledgment and before return, the parent retains the full precommitted superset as `POSSIBLE_DOWN`; it may reduce that set only after producer retirement and independent neutral-state readback. A child that does not receive the acknowledgment is forbidden to call the API.

**Q02 — compensation authority.** Process exit and a held-key ledger do not prove exclusive ownership of the input stream. A private desktop ACL can constrain access to desktop objects, but the cited Windows contracts do not show that it scopes `SendInput` to that desktop; a private/non-active desktop alone is therefore insufficient isolation evidence. The candidate grants compensating UP authority only inside a disposable Windows VM and dedicated interactive logon-session/input scope whose machine-verifiable harness attestation proves the actual input route, VM/session generation, window station/input desktop, exclusive coordinator lease, and an input-source policy excluding concurrent human or other-process injection for the test interval. If that end-to-end containment cannot be demonstrated on the target Windows configuration, compensation is unauthorized and the native qualification remains HOLD. Before admission, an independent state observer must report every reserved key/button neutral with a valid observer-health receipt; unknown is not neutral. The recovery process may release only the keys/buttons in that operation's precommitted `POSSIBLE_DOWN` set while the same isolation lease remains valid. Missing/expired attestation, preexisting-down state, unrelated input activity, or uncertain observer health means no compensation is authorized: retain `UNKNOWN`, deny replay, and keep that generation quarantined. Shared desktop compensation is out of scope.

**Q03 — quarantine exit.** Process retirement, one neutral sample, and elapsed time—even a predeclared late-DOWN horizon—cannot clear an unresolved operation in the same input generation. A same-generation exit would require a platform receipt that definitively drains/cancels every admitted event plus independent neutral readback; the cited Win32 contracts provide no such receipt, so this proposal has no automatic same-generation clearing transition. A fresh operation may instead run in a distinct isolated VM/logon-session generation only after the old generation is retired and cannot receive input, the new generation has a verified task precondition/checkpoint, and fresh target-generation evidence and admission are created there. The old operation remains `UNKNOWN`, `replay_allowed=false`, and immutable; the new task is a separately identified attempt, not a retry of the old action. If any retirement, setup, or precondition check misses its bound, recovery remains `PENDING`/`UNKNOWN` and no input is sent.

This boundary is a candidate, not a qualified architecture. Process retirement may stop future user-mode submissions without proving that an already accepted event cannot take effect later. The prototype must therefore include a late-DOWN discriminator: exercise calls blocked both before and after acceptance, retire the producer, attempt recovery only after the ownership boundary, and observe whether any DOWN appears after the accepted recovery point through a declared horizon.

## Alternatives

1. **Recovery thread in the existing process — reject for bounded release.** It cannot preempt a synchronous caller or fence late producer work. The R01 probe also shows public recovery can refuse while the modeled key is held.
2. **Prestarted supervisor with disposable operation and recovery processes — preferred falsifiable prototype.** It provides an observable producer-retirement boundary and keeps a bounded caller-response path. It is acceptable only if both admission schedules pass, including native late-DOWN observation and independent readback.
3. **Target-specific API with server-side generation and expiry — preferred production route where available.** It can bind authorization and effect to target state, but is not a general desktop backend and needs separate integration and effect evidence.

Reject the supervisor prototype if an old DOWN can arrive after confirmed child retirement and recovery, if release state cannot be independently observed, or if a fresh target's task effect cannot be checked.

## State and failure semantics

- Only the supervisor admits an operation and owns its identity, deadline, child identity, and recovery state.
- The supervisor binds the child to one operation identity and waits for readiness before admitting input. Cancellation first closes admission for that operation, then requests child retirement.
- Child retirement is `CONFIRMED` only after the exact child process handle is signaled within the configured bound. Timeout, lost IPC, or ambiguous identity is `UNKNOWN`.
- The exact possible-down set is durably reserved and acknowledged before the first native input call; the child cannot send before that acknowledgment.
- Recovery cannot start while the producer may still emit. A refusal or timeout is not release confirmation.
- Compensating UP is authorized only by the operation's reserved possible-down set and a live, verified private-input-scope lease; it is never inferred from a process exit or a global release request.
- Independent state readback is a separate observation with its own deadline and raw evidence.
- Any unresolved producer, failed recovery, or unavailable observer leaves the result `UNKNOWN`, denies replay, and keeps new input fenced.
- A finite horizon never clears an UNKNOWN operation in the same input generation. Fresh work requires an independently created isolated generation and verified task precondition; the old result stays UNKNOWN and is not replayed.
- A task is successful only when a fresh target's effect is checked independently from the input sender's receipt.

## Validation gates

1. **Inert state-machine tests:** cover startup blocked before readiness while cancellation/status remains responsive, journal-flush stall with no input acknowledgment, child exit/lost IPC after possible-down reservation, late child startup after admission expiry, stale/duplicated one-use capabilities, HWND reuse with a different PID/process-creation identity, generation change after model wait and immediately before input, preexisting-down/unknown baseline, absent/expired isolation attestation, rejection of UP outside the reserved set, refusal to clear UNKNOWN by timer/readback alone, fresh-generation recovery with old-result preservation, process/readiness timeout before admission, blocked-before-acceptance and accepted-before-return, child-retirement timeout, IPC loss, recovery-owner failure, stale operation IDs, repeated cancellation, and prevention of overlapping producers. Run focused tests normally and with Python optimization enabled.
2. **Platform semantics review:** check process and input-queue behavior against primary Windows documentation. If accepted-event cancellation remains unspecified, keep the native safety claim open.
3. **Isolated native discriminator:** only with a verified disposable target, exercise both schedules and preserve OS/process identities, timing bounds, raw event and independent-state observations, late-DOWN horizon, and independent task effect. No desktop-wide input is implied.
4. **Standard-caller integration:** begin only after the ownership protocol passes. Then run matched baseline/recovery measurements for response latency, release-confirmation coverage, late-input count, and task correctness. Reliability needs independent repetitions under a predeclared policy.

## Explicit non-goals and current evidence

This design does not claim bounded release, Windows qualification, successful task effect, matched efficiency, or reliability. It does not authorize runtime implementation, native-input execution, WSLc/Docker use, or a new allocation. The current result remains `UNKNOWN`.

The existing Win32 evidence checkpoint and synthetic schedule are recorded in [`docs/architecture/PRESTARTED_CANCEL_SUPERVISOR_DESIGN.md`](../../architecture/PRESTARTED_CANCEL_SUPERVISOR_DESIGN.md), including the limitations of the R01 fake API result. This standalone specification makes the candidate and its falsification gates reviewable; it does not replace that evidence record. The historical Xvfb specification at this directory's `2026-10-22-prestarted-cancel-supervisor-design.md` is preserved independently and covers a different route.
