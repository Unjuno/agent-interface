# Deferred cancellation custody: design to evaluate

Status: proposal, not implemented. The r517 subprocess counterexamples show that a daemon cleanup thread can lose its final receipt during graceful parent exit, while simply making that thread non-daemon can block parent exit on a stalled writer. They use a fake owner and do not validate real producer or supervisor retirement.

An independently surviving guardian is one candidate. On Linux it could be started and bound to exact owned process generations before an input operation is admitted, with pidfds transferred over a private channel. A readiness acknowledgement must establish that the guardian has accepted each descriptor and the frozen custody record; failure or ambiguity must not grant permission to start an operation that depends on this recovery path. Platform alternatives include an existing external supervisor or a suitable OS lifecycle mechanism; this proposal does not require one implementation across platforms.

On shutdown timeout, the parent would give the guardian a uniquely identified, single-use cancellation and cleanup obligation. A durable or independently retrievable acknowledgement must bind the operation ID, owner generation, input obligations, deadline, and guardian identity. Parent exit may proceed only under a clearly defined handoff policy; timeout, guardian loss, ambiguous acknowledgement, or failure to establish identity remains UNKNOWN and does not authorize replay. The guardian must never release input on an arbitrary shared display based solely on a PID or mutable name; terminating an exactly owned producer does not prove queued X requests drained or key-up occurred.

Guardian work must have bounded waits and isolate filesystem writing from process retirement so a stalled writer cannot prevent retirement or falsely produce a receipt. A receipt must distinguish process observed dead, release attempted, release verified, task outcome, and evidence persistence. Hard real-time guarantees cannot be inferred from timeout parameters alone. SIGKILL or abrupt power loss may prevent any final receipt; missing evidence is UNKNOWN. No automatic replay follows recovery.

Before integration, test at least: parent exits before/during/after handoff; guardian exits at each point; duplicate or mismatched operation IDs and stale process generations; actual owned child and supervisor still alive versus already exited; a blocked receipt writer; cancellation finishing just before/after deadline; a bounded non-blocking parent exit with custody independently observed after exit; and negative controls for unrelated processes, old-release delivery and a delayed request. Preserve raw timestamps and process identities. Test both successful and failed handoff and retain unresolved outcomes rather than converting them to passes.
