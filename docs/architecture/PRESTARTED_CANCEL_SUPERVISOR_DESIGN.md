## Design review checkpoint (2026-10-22)

The user selected this design as the first repository-organization work item. The opt-in runtime integration is merged by [#9320](https://github.com/Unjuno/agent-interface/pull/9320); its retained implementation and experiment packets were transferred by [#9321](https://github.com/Unjuno/agent-interface/pull/9321). Keep the supervisor default-off and treat it as an experimental path, not a production guarantee.

The architecture must keep these claims separate: (1) the MCP caller returned within its response deadline; (2) evidence shows the retired owner's connection no longer owns its XRes base; (3) a release was issued and independently read back; (4) a task oracle verified the intended effect; and (5) a fresh target recovered within a finite bound. XRes reports the current PID at a resource base, and a retired base can be reused. The merged runtime accepts two disconnect observations: the base is absent, or the prestarted supervisor's own live X client now owns that base. X resource bases are unique among concurrently live clients, so seeing the supervisor PID at the retired base means the old owner no longer owns it. If an unrelated PID claims the base first, the worker fails closed with `UNKNOWN` and does not release. The two-display Ubuntu/WSL diagnostic reproduced supervisor-owned and bystander reuse; the public-caller worker tests cover the accept/reject split. This proves neither delayed-request queue drainage nor owner-exclusive physical state. Even a successful global key-up readback does not establish which client owned that key.

The decision is **retain the merged opt-in supervisor and its conservative XRes reuse rule; do not treat this path as generally qualified**. The focused XRes owner-PID/reuse tests pass 11/11 in normal and optimized Python. More importantly, the retained [PR #9320 standard-caller Xvfb run](../../research/integration/public_mcp_prestarted_cancel_supervisor_20261021/pr9320-run-39660663702/README.md) exercised a held obligation while the owner was blocked in `Display.sync()`: the supervisor reused the retired base, issued one release, and an independent client read the key up both immediately and after the injected 8-second delayed-request horizon. The independent synthetic task oracle passed. The public runtime receipt nevertheless remained `cleanup_status=UNKNOWN`, `release_confirmed=false`, `task_success=null`, and replay denied because `late_server_request_possible=true`. This is a scoped positive end-to-end outcome and a conservative runtime classification, not a contradiction or a reliability estimate. A separate local R32 follow-up restored close reservation after pre-entry rejection and passed focused close-retry cases in both modes; it is not represented here as merged. Keep the supervisor default-off. Next qualify fresh-target recovery and the boundary for retaining or clearing `late_server_request_possible` after an independently observed horizon, then measure matched efficiency and reliability. Keep Issues [#17](https://github.com/Unjuno/agent-interface/issues/17) and [#57](https://github.com/Unjuno/agent-interface/issues/57) open while their safety-plane and integrated-efficiency questions remain unresolved. WSLc remains HOLD under Issue [#7924](https://github.com/Unjuno/agent-interface/issues/7924); no WSLc allocation was used for these results.

## Goal and constraints

Make `interface_guarded_cancel` return within a monotonic caller-response bound while preserving one cancellation/cleanup operation's custody through a finite deadline. A response timeout must remain `UNKNOWN` or `pending`; it must never imply that physical input was released, that the task succeeded, or that input may be replayed. A late or stale cleanup request must not emit a new effect after its deadline or against a different owner generation. The safety path must not depend on planner delivery, image/JSON serialization, ordinary journal persistence, stdout, or event subscribers; critical safety outcomes are recorded best-effort after the action and cannot synchronously delay it.

This design applies to the opt-in `guarded-x11` owned-process path. It preserves FINAL v5 and current execution assignments, keeps `task_success` null absent an independent task oracle, and uses no new WSLc allocation. It does not claim a universal release guarantee when X11 or the OS cannot service input or readback.

## Retained-result seam audit (2026-10-21)

The fetched `main` tip for this audit is `3104de8508f2676242a42847a626db9a4ac82934`; the relevant runtime files are byte-for-byte identical to local source `e7d79d04de46202622873bf116adb909abb0dee2`. `create_server` registers `interface_guarded_cancel` as an async MCP tool, but the registered handler directly returns the synchronous `cancel(call_id)` callback. That callback reads the current `calls` entry under `calls_lock` and then returns `owner.cancel_guarded(call_id)`; it does not write the returned cancellation receipt into the call record or a separate retained file.

`interface_results(call_id)` is the existing read-only retrieval path. It reports `pending` while the original action worker is running. After that worker finishes, it reads the original action's `report.json` (or its interruption receipt) and returns that action outcome with the retained call metadata. Current Fake X tests verify that a cancellation can retire a blocked owner and that the eventual original call result remains conservative. They do not establish a separately retained lifecycle for a cancellation operation that outlives its tool response.

**Decision for the proposal:** keep `interface_results(call_id)` as the sole retrieval endpoint. Give the cancellation transaction its own operation ID and store an additive `cancellation` subrecord in the original call's in-memory registry entry and call directory. The subrecord has `pending`/terminal status, owner generation, absolute deadlines, stage receipts, worker retirement, and uncertainty; it never overwrites the original action report or promotes `task_success`. A call with pending cancellation remains visible through the existing call ID. This avoids a second public tool while preserving the distinction between action and cancellation evidence.

The [standard-caller duplicate-cancel retention characterization](../../research/integration/standard_caller_duplicate_cancel_retention_20261021/README.md) is the current baseline: one release-helper call, but the second request returns `not_active`, no cancellation operation ID is returned, and `interface_results` has no cancellation subrecord. The independent-owner duplicate-cancel PASS in #814 is a separate semantic result and is not repeated here. The next discriminating Fake X validation must exercise a prototype registry/supervisor through the public MCP caller: retrieve the original action while cancellation is pending and after terminal completion, verify separate action/cancellation records, show duplicate requests share one operation ID and one release attempt, and retain `UNKNOWN`/no replay on timeout or stale generation.

The proposed 300 ms caller deadline, 450 ms outer response ceiling (including 150 ms scheduling/serialization slack), and 3 s transaction deadline are provisional local test targets, not user-visible compatibility guarantees. The feasibility probe supports only the construction-level 300 ms pending transition under its injected schedule; it does not qualify the outer ceiling or a production transaction bound. Keep these values centralized and configurable for the opt-in mode. Before any promotion, compare them with the current source constants, run under local load, and preserve measured admission-to-response and admission-to-terminal durations separately. A passing timing target cannot promote a release or task-success claim.

## Proposed architecture

Add one narrowly typed, persistent `OwnedCancellationSupervisor` process for each opt-in owned guarded session. Start it and wait for a readiness receipt before admitting guarded input. It owns a command/result channel and accepts only one cancellation transaction; it does not expose generic remote execution. The prestarted process itself performs the bounded XRes disconnect query followed by the one release/readback operation. It does not call `Process.start()` during cancellation, so the transaction has no per-cancel helper-process startup. A synchronous Xlib call that hangs is contained in this helper process, which its parent can terminate at the operation deadline.

Prewarm a dedicated one-worker cancellation executor before serving requests. The async MCP endpoint submits `OwnedGuardedSessionOwner.cancel_guarded` to that executor with `loop.run_in_executor`; it awaits the result only until the caller-response deadline and shields the one in-flight operation from request-task cancellation. The executor thread performs owner control/retirement and communicates with the prestarted cleanup process. The event loop remains available to serve result lookups and unrelated MCP calls. A bounded per-server cancellation map makes repeated cancel calls idempotent and carries a late terminal result into `interface_results`. The request carries:

- a random operation ID and the guarded call ID;
- the immutable owner generation tuple captured from the opened owner (session ID, child PID, X resource base, and binding revision);
- one absolute `deadline_monotonic_ns`, created at cancellation admission;
- the cancellation token and, after owner retirement, the validated owner-input-obligation snapshot.

The supervisor serializes these stages against that same absolute deadline:

1. Request cancellation on the exact active owner using the remaining transaction budget and retain its response or classify it as unconfirmed.
2. Retire the owner when the existing late-server-request or held-input rules require it. Do not reopen or replace it.
3. Send one typed cleanup request to the ready supervisor. The supervisor confirms the exact retired client's XRes disconnect using the captured owner identity.
4. Only after confirmed disconnect and a valid obligation snapshot, attempt one release/readback operation in the same prestarted process. Before connecting or emitting any `KeyRelease`/button-up request, the process checks the original deadline and owner-generation tuple.
5. Retain the stage receipts, supervisor PID/exit evidence, and terminal classification. A missing reply, expired deadline, unsupported identity, blocked server request, supervisor-start failure, or unclean supervisor exit stays `UNKNOWN`.

The MCP caller returns the completed receipt if it arrives in time. If the caller-response deadline expires first, it returns `pending`/`UNKNOWN` with the operation ID and no release claim. The transaction keeps custody; duplicate cancellation calls for the same call ID return the existing operation state and do not enqueue another release. The existing result lookup must expose the retained terminal cleanup receipt after the supervisor finishes. No retry, reconnect, new input, or replay is allowed while cleanup is outstanding or unknown.

Use distinct but nested budgets: the caller-response deadline is shorter than or equal to the transaction deadline. Both are absolute monotonic timestamps derived at admission, not fresh per-phase durations. Proposed initial values are a 300 ms caller wait and a 3 s whole-transaction bound, matching the Fake X construction probe and existing cancellation target. The API response must be returned by 450 ms from admission, allowing the probe's explicit 150 ms scheduling/serialization slack; at the 300 ms caller deadline its state is already `pending`/`UNKNOWN`. These values must be confirmed against current source constants and tested under local load before promotion. Time spent in IPC, process start, owner retirement, XRes, release and reap all consumes the transaction budget.

If the supervisor cannot finish by the transaction deadline, the executor thread terminates it and classifies cleanup `UNKNOWN`; the owner/session becomes unusable and custody metadata is retained. Do not claim that killing the helper retracts requests already queued in the X server. No subsequent owner may inherit the old generation or cleanup receipt. The cleanup helper is retired at owner close when no cancellation consumed it.

## State and compatibility rules

- `release_confirmed` is true only after an accepted release result, clean worker exit, and independent release readback for the exact operation and owner generation.
- Every timeout, malformed receipt, stale generation, process-start delay past deadline, blocked X request, or unclean worker exit yields `release_confirmed=false`, `cleanup_status="UNKNOWN"`, `task_success=null`, and `replay_allowed=false`.
- A bounded caller response and physical release remain separate observations. Returning `pending` does not authorize another input call.
- Existing non-owned and non-X11 modes keep their current cancellation path.
- Existing terminal call receipts and raw attempt evidence remain immutable. New cancellation evidence is additive and names its operation ID, deadlines, stage timestamps, owner generation, worker PIDs/exit codes, readback source, and uncertainty reasons.
- Startup must fail closed for the opted-in mode if the cancellation supervisor cannot become ready; do not silently fall back to synchronous cancellation.
- Bound the number of live supervisors and cancellation records per server using the existing guarded-session capacity. If the current capacity is not explicit, define a finite opt-in limit before enabling the path; exhaustion fails closed and cannot evict pending custody.

## Main risks and unresolved design choices

The prestarted supervisor removes per-cancel child creation from the response path, but it does not make OS scheduling, Xlib requests, or process termination mathematically bounded. The final release boundary must check the absolute deadline because the supervisor may be scheduled late. The existing XRes `(resource_base, PID)` identity is not a cryptographic generation token, so generation fencing must also bind the session ID and permanently retire the session after cancellation. XTest key/button state is global to the X server; the current readback does not prove that the retired owner was the only client holding that key or button. Unless an exclusive-input condition is established independently, a successful global release readback is not sufficient to claim owner-specific release. Cancellation executor capacity must remain one and bounded; timed-out futures cannot create a second concurrent cleanup operation.

The bridge's monotonic input lease bounds one method's dispatch interval; it does not reserve global X11 key/button state against another client. The supervisor request currently has no independent exclusive-input lease or capability. Therefore owner-PID absence or supervisor-PID reuse is identity evidence only, not authorization for a shared-desktop global XTest release. A future promotion must either establish and validate exclusive input authority through cleanup or fail closed without emitting the global release event; synthetic single-owner fixtures do not satisfy this condition for a shared desktop.

This also implements only one possible shape of the separate safety/data-plane split requested by Issue #17. The safety control path must not wait on the existing receipt write path, while compact post-action status may degrade to `DATA_PLANE_BLOCKED`. A two-owner race, planner-controlled release, telemetry lock on cancellation, or false `RELEASE_CONFIRMED` would reject the design even if response timing passed.

The source audit supports `interface_results(call_id)` with a separate additive `cancellation` subrecord; a second public tool is not needed unless the composed Fake X test proves that this existing result path cannot preserve pending and terminal cancellation state independently. Treat the response/transaction values above as provisional test targets and resolve them from focused local measurements and existing source constants before promotion; no policy decision or user-visible guarantee is implied by this design note.

## Target-lifecycle final-check race analysis (2026-10-22)

The local standard-caller regression packet reproduces the remaining destroy-gap precisely: `_verify_process_identity_for_press()` returns from the separate lifecycle query worker; the input owner prearms the key-release obligation; a `DestroyNotify` is then delivered to and drained by that query worker; and the owner emits the first XTEST `KeyPress` before the subsequent press observes the retired reader. X.Org documents that X11 only preserves request order per client connection, without a global order across clients ([X.Org communication overview](https://www.x.org/guide/communication/)).

`XGrabServer` is not an acceptable quick fix for this path. If the owner blocks while holding the server, the proposed atomicity mechanism can prevent the recovery path from progressing. Keep the current fail-closed review/release behavior and record the residual race; do not add a server-wide grab without a separately proven bounded unlock and cleanup design.

Closing this gap requires a server-ordered primitive that binds target incarnation to the input request, or a supported application's own target-scoped control API, while retaining independent bounded cleanup. The XTEST/Fake-X checks above do not prove that such a primitive exists, and no replacement has been implemented. Keep this boundary open rather than treating the locally released key prefix as a correct task effect.

## XTEST deadline semantics source audit (2026-10-22)

The XTEST protocol defines the `time` field of `XTestFakeInput` as either `CurrentTime` (no delay) or a relative delay in milliseconds; the server waits for that delay before simulating the event, and does not process later requests from that same client until the event is processed ([XTEST protocol specification, pp. 6–7](https://www.x.org/releases/X11R7.6/doc/xextproto/xtest.pdf)). Xlib `XSync` flushes buffered requests and waits until all preceding requests have been received and processed ([Xlib specification, §11.8.1](https://www.x.org/releases/X11R7.6/doc/libX11/specs/libX11/libX11.html#XSync)). X.Org's protocol overview states that request order is per connection and that the server does not guarantee ordering between separate clients ([X.Org communication overview](https://www.x.org/guide/communication/)).

**Inference and scope:** these documented XTEST/Xlib interfaces provide no server-enforced absolute monotonic deadline or cancellation token that retracts an already accepted input request when the caller's deadline expires. Terminating a blocked helper bounds the parent-side wait, but cannot by itself prove that a release request already buffered or accepted by the server will have no later effect. A second XTEST connection also does not establish an order relative to requests from the retired connection. This source audit does not prove that every X server implementation has identical buffering behavior, nor does it establish physical key state; an implementation-specific live test would still be needed for any narrower claim.

Consequently, the current XTEST path supports only a bounded caller response and a bounded helper-retirement attempt under a server stall. Release-effect bounds while X11 is unavailable remain unproven. The next architectural discriminator must evaluate a server-side expiring/fenced input primitive or a distinct OS input backend with independently verified authority, release semantics, and application effect. Reissuing XTEST through another connection or adding a client-side timeout alone does not close this gate. No implementation or new allocation was started by this source audit.

## Win32 operation-owner design checkpoint (2026-10-22)

### Requirements and source boundary

The required outcome is a bounded cancellation response **and** bounded input neutralization while an input API call is blocked, followed by independent platform-state readback and independently checked task effect on a fresh target. Bounded return alone is not release. Until every item is observed, the operation result remains `UNKNOWN`, replay remains denied, and no new input operation may overlap a producer whose retirement is unresolved.

Current `Win32RuntimeSession.dispatch()` and `Win32Backend.execute()` call `SendInput` synchronously. The backend adds the held-key ledger entry only after `SendInput` returns; `recover_input()` refuses before attempting release unless `recovery_required` is already true. The R01 accepted-before-return probe confirms one schedule where the platform-state model is down while both bookkeeping conditions say recovery is unnecessary. Source inspection also predicts a second schedule: if a DOWN call is blocked before acceptance, cancellation cannot advance the same synchronous dispatch, and that dispatch may still submit DOWN when the call resumes. This second schedule is a source-derived prediction, not a separately captured test outcome.

Microsoft documents `SendInput` as inserting supplied events serially and returning the number inserted. Its documented signature exposes no deadline or cancellation handle. Those statements do not establish what terminating a process with an in-flight call does to input already accepted or queued; that consequence must not be inferred from process death alone ([Microsoft `SendInput` reference](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-sendinput)).

### Candidate ownership boundary

The next candidate to evaluate is a prestarted supervisor that is the only parent-side owner of operation state and creates a disposable child process for each bounded input operation. The child performs at most one admitted program and reports only through a bounded IPC receipt. At expiry/cancel the supervisor first prevents admission of further work, then retires the exact child process, waits only to a fixed deadline, and records retirement as confirmed or unknown. A distinct prestarted recovery process may submit compensating UP events only after producer retirement is confirmed; an independent observer then reads key/button state. If process retirement or state readback misses its bound, the supervisor reports `UNKNOWN`, denies replay and keeps new input fenced.

This is a candidate, not a qualified architecture. In particular, process termination may stop further user-mode submissions without proving that an already accepted event cannot take effect later. Therefore the key acceptance condition is a late-DOWN discriminator: force the operation child to block before and after acceptance, cancel and retire it, attempt recovery only after the owner boundary, then observe that no DOWN appears after the accepted recovery point through a declared horizon. The harness must preserve both the supervisor response bound and independent state transitions. A fake API can validate state-machine ordering but cannot qualify Windows behavior; any later native fixture must use a disposable, isolated target and separately prove the target's task effect.

The process boundary itself may also exceed the release budget: Microsoft documents `TerminateProcess` as asynchronous and says the process cannot exit until pending I/O has completed or been canceled; confirmed retirement requires waiting on its process handle. The documentation does not establish whether an in-flight `SendInput` maps to pending I/O for this rule. Therefore the supervisor may return `pending` at its caller deadline, but it must not authorize a second sender while the old child is still live or retirement is unknown. A wait timeout is a bounded caller result, not a producer fence or a release result ([Microsoft `TerminateProcess` reference](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-terminateprocess)).

### Options and decision

1. **Recovery thread in the existing process:** reject as a bounded-release design. It cannot preempt the synchronous caller, does not fence late producer work, and the R01 probe shows public recovery can refuse while the modeled key is held.
2. **Prestarted supervisor plus disposable operation/recovery processes:** preferred as the next *falsifiable prototype*, because it creates an observable producer-retirement boundary and lets the parent keep a bounded response path. Do not claim release safety unless the accepted and not-yet-accepted schedules both pass, including native late-DOWN observation and independent readback.
3. **Target-specific application control API with server-side generation/expiry:** retain as the preferred production route when a target offers one, because it can bind authorization and effect to the target's own state. It is not a general desktop backend and requires its own integration/effect evidence.

The preferred prototype is rejected if the platform can deliver an old DOWN after confirmed child retirement and recovery, if release state cannot be independently observed, or if a fresh target's task effect cannot be checked. No runtime implementation, API change, or native-input run is authorized by this checkpoint; implementation starts only after review of this written design and a separate implementation plan.

### Validation sequence and remaining gates

1. Use only inert process/API fakes to test both admission schedules, child-retirement timeout, IPC loss, recovery-owner failure, stale operation IDs, repeated cancel, and no overlapping producer. Run focused tests normally and under `-O`.
2. Review the candidate's Windows process and input-queue semantics against primary documentation. If documentation leaves accepted-event cancellation unresolved, keep the native safety claim open rather than treating the fake as proof.
3. Only with a verified isolated native target, test a fresh target after both schedules; record exact OS/process identities, timer bounds, raw event/state readback and independent task effect. No WSLc/Docker allocation or desktop-wide input is implied by this design.
4. Integrate through the standard caller only after the ownership protocol passes. Then perform matched baseline/recovery experiments for response latency, release-confirmation coverage, late-input count and task correctness; reliability requires independent repetitions under a predeclared policy, not one successful trace.

The current result remains `UNKNOWN`. This checkpoint narrows the design choice but does not complete bounded release, target-generation composition, observation/effect timing, task success, efficiency, or reliability.
